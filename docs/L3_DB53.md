# L3 DB53: turns Store size hint for grok ord / dense RSS (G-DB51-2, G-DB51-4, G-DB51-3)

Brief: (1) G-DB51-2, ord fixed RSS above hand because the turns Store data buffer grows 64 K -> 136 K -> 279 K ->
561 K before DB48's 4,259,840 jump: let turns take a size hint from the window (only above 1 MiB of text) and keep
the proved bounds; ord M/L RSS at or under hand, dense not worse. (2) G-DB51-4, dense M/L RSS above hand (fixed 1.84
vs 1.72 MiB): attribute the fixed part with an allocator trace and cut it if it lies in grok or turns. (3) only if
time is left, G-DB51-3 (ord / dense M/L time on rs/llvm, py/rust, py/llvm). Base: main 74f53293. One release
`pruvc-rs` build from this base; no compiler change.

## What landed

- `bench/l3/pkgs/turns/turns.pruv`: `Store` gets a field `hint` (the owner's input size, 0 = unknown) and a
  constructor `new_store_hint(hint)`; `new_store()` is `new_store_hint(0)`. Only `reserve`'s new-buffer size reads
  the hint:
  - with a hint the smallest buffer is 16,384 bytes instead of 65,536 (item 2: a dense window keeps a few KiB of
    live text);
  - with a hint over 1 MiB, the first grow past that smallest buffer goes straight to 4,259,840 bytes, the size
    DB48 already jumps to once a grow passes 1 MiB (item 1). A window whose text stays in the first buffer never
    takes that grow, so it never maps the large buffer; this is why the hint is in `reserve` and not a pre-sized
    Store in grok (the DB51 experiment that cost dense L 65 KB).
  The proved bounds are unchanged: the loop invariant `tgt <= cap` still holds because `tgt <= 2,129,920 <
  4,259,840` and the 16,384 floor only applies when `2 * tgt` is below it. Contents, offsets, the dropped-draft rule
  and the packet are the same for every input; only the buffer sizes differ.
- `bench/l3/grok/read.pruv`: `window()` builds its Store with `new_store_hint(n)`, `n = len(win)`.
- `bench/l3/grok/perf/perf_driver.rs`: the `rss` mode prints the packet fold after the run, so every RSS sample
  is compared with hand (the brief's rule; before, only the `time` samples were).
- `turns` is also used by `bench/l3/qwen/import.pruv` (`new_store`, `begin2`, `answer2`), not only grok as the
  brief says. qwen keeps `new_store()` (hint 0), whose sizes are exactly the old ones.

`perf/run_perf.py check`: every row `pruv == hand` on all four pairs (Checks below); the folds are the same as DB51
(ord-2m 5100153930953742342).

## Allocator trace (item 2)

A counting `#[global_allocator]` (in a scratch copy of the generated rs/rust crate in /tmp, deleted) logged every
allocation of one `window` call. Peak heap over the process base:

| row | pruv before | pruv after | hand |
|---|---|---|---|
| dense-2m | 227,372 B: packet 118,912, Store data 65,536, rows 16,000, `sl` 12,800, stamp 9,600, off 1,600 | about 178,000 B (Store data 16,384) | 146,120 B: packet 118,912, rows 24,000 |
| 3 KB slice of dense-2m | 94,812 B | about 46,000 B | 26,168 B |

The 64 KB first Store buffer was the largest grok / turns part of the dense gap; it is now 16 KB. What is left of
the dense fixed gap is about 100 KB, the same on a 3 KB input (pruv 1.75 MB, hand 1.65 MB peak RSS), and splits as:

- about 22 KB of heap: the turns ring state `sl` (1,600 i64) and `stamp` (9,600 B), both live for the whole window
  and sized by the 200-slot ring, against hand's per-turn rows; shrinking them changes the ring layout every
  `begin2` / `answer2` / `begin3` / `answer3` proof relies on (G-DB53-2);
- the rest is not heap: it matches the extra code pages of the generated Rust (`nm` on the rs/rust driver:
  `pruv_impl` text 77,440 B, of which `window` 53,940 B after inlining, against hand's 16,880 B), which is
  compiler / codegen output, outside this lane (G-DB53-1).

## Decisions

| id | decision | why | status |
|---|---|---|---|
| D-DB53-1 | the size hint lives in the turns `Store` (`new_store_hint`) and only `reserve`'s buffer size reads it | a window whose text stays in the first buffer never maps the 4,259,840 B buffer, so dense does not pay what the DB51 grok-side pre-size cost (65 KB on dense L); the contents never depend on it | kept |
| D-DB53-2 | with a hint the first buffer is 16,384 B, not 65,536 B | dense windows keep about 3.6 KB of live text; the trace showed the 64 KB buffer as the largest grok / turns part of the dense fixed gap; ord windows leave it on the first grow either way | kept |
| D-DB53-3 | `new_store()` stays, as `new_store_hint(0)` with the old sizes | `bench/l3/qwen/import.pruv` uses it and is outside this lane | kept |

## Gaps

| id | gap | cause | next |
|---|---|---|---|
| G-DB53-1 | dense M / L RSS still above hand (1.025x / 1.008x; fixed 1.85 vs 1.76 MiB); about 60-80 KB of the gap is not heap | the generated Rust for the read path is about 60 KB more code than hand (`pruv_impl` text 77 KB, `window` 54 KB after inlining, hand 17 KB) and its pages are resident | compiler / codegen lane: measure text size per function on both backends, cut inlined duplication (e.g. proof-only or repeated checks in `window`), re-measure dense M/L RSS |
| G-DB53-2 | about 22 KB of the dense heap gap is the turns ring state (`sl` 12,800 B, `stamp` 9,600 B) | both are sized by the 200-slot ring and live for the whole window; hand keeps only per-turn rows | turns lane: a smaller ring layout (e.g. stamps inside the data records) means re-proving `begin2` / `answer2` / `begin3` / `answer3` and `reserve`; only worth it together with G-DB53-1 |
| G-DB53-3 | ord M / L time above hand on rs/llvm and py/llvm (load 4: 1.071x / 1.038x and 1.068x / 1.034x; rs/rust 0.993x / 0.978x) | not load and not new in DB53 (old 1.09x / 1.045x); same Pruv source as the Rust backend, so it is the LLVM backend's code for `window` (the `sample` shape matches; the zeroed packet, G-DB51-1, is about 4% on both) | compiler lane: instruction-level profile of `window` on LLVM vs Rust backend (UTF-8 validation, bounds checks, memmove), fix the codegen, re-measure ord M/L on both LLVM pairs |
