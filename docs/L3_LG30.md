## Step 1: the byte after an ASCII byte (G-DB47-2)

`W(b, lo, n)` (R-6b-3, `utf8_window` in `pruvc/verify.py`, the same encoding in `pruvc-rs/crates/pruv-proof/src/model.rs`) states for every
`0 <= i < n` that `b[lo + i]` is ASCII, or a lead byte whose continuation bytes follow inside the window, or a
continuation byte that completes a lead byte one to three bytes before it. Take `i` with `i + 1 < n` and
`b[lo + i] < 128`. Instantiate `W` at `i + 1`: the continuation disjunct needs `b[lo + i]` to be a lead byte (2-byte
form) or itself a continuation byte (3- and 4-byte forms, which also look further back through `b[lo + i]`). Both are
`>= 128`, a contradiction, so `b[lo + i + 1]` is ASCII or a lead byte: a char boundary. Hence a run `b[q..e)` with
`b[q - 1] < 128` and `b[e] < 128` (or `e` the end), inside a valid span, starts and ends on boundaries, and its own
`W` follows from the outer one instance by instance.

Rule decision: the fact is a consequence of the exact model, so it is stated in SPEC R-6b-3 as derived, not added
as an axiom. No compiler code changes, nothing is added to the trusted base, and both compilers already emit the
same `W` (diff_trace). The solver proves it when the program states the previous byte is ASCII; `dstr` does so
with `requires b[p - 1] < 128` (`p` follows the opening quote) and the loop invariant `b[q - 1] < 128` (every run
starts after the quote or after a one-byte escape letter). `kind_of` gains `ensures result == 4 ==> c == 34` so the
caller can discharge the new `requires`. The deleted line was the run-time test `a >= 128 && a < 192` on `b[q]`.

Negative probes: the same copy is rejected when the byte before the run is a lead byte
(`tests/must_reject/lg30_after_lead.pruv`) and when the ASCII byte lies outside the valid span
(`tests/must_reject/lg30_outside_span.pruv`), both at the copy's `ensures utf8_valid_span(d, 0, result)`.

## Step 2: per-occurrence guards of opaque applications (G-LG29-1, G-LG28-5)

`st.apps` held `(f, app, args)` and `app_ids` the first occurrence of each application id, so the body of an
opaque application was evaluated with an empty guard both when it was unfolded at once and when a later `reveal`
added its equation. The W facts that evaluation pushes (the `str` reads of the body) were therefore assumed with no
guard, though the application might be evaluated only under a path condition.

Rule decision: `st.apps` now holds `(f, app, args, guard)` for every occurrence, keyed in `app_ids` by
`(app id, guard ids)`; the first occurrence of an id adds the definition equation `app == body` unguarded (it is
true everywhere, R-6o-4), and every occurrence evaluates the body under its own guard so the W facts it pushes are
`Implies(guard, W)`. Each occurrence also keeps the bound variables of the quantifiers around it (`qstack`); the body is evaluated with
`qstack` set to them, so a W fact from a later `reveal` is `ForAll(qs, Implies(guard, W))` and does not lose the
bound variable (audit must-fix). `reveal` walks the stored occurrences (one equation per id). Python (`opq`, `opq_occ`,
`opq_body`, `reveal`, `hidden` in `pruvc/verify.py`) and Rust (the same names in `symbolic.rs`) mirror each other;
diff_trace shows no hard diff.

Evidence: `tests/runtime/lg30_opq_guard.pruv` applies `hit(p, 0)` under `p.n > 0` and, after `reveal hit`, under
`p.n < 0`. Its Python trace (`tests/diff_py_adapter.py trace`) has the W of `p.label` as
`(=> (and (< 0 p.n) (<= 0 0)) (forall ...))` and `(=> (and (> 0 p.n) (<= 0 0)) ...)`: each under its occurrence's
guard. Its `late` function applies the opaque `edge(p)` inside `forall i in 0..1` in a `requires` and reveals it in
the body; before the qstack fix its `ensures` failed (the bound variable leaked out as a free constant), with the fix
and at 1ff844a9 it verifies. No must_reject test can show the guard difference yet: a `str` value is valid by type, so an unguarded W of a
`str` read is never false (G-LG28-1).

## Step 3: G-LG29-3 not started

Picking the slot read as a default pattern needs new trigger-selection code in both compilers (with the same
trace), then a proof sweep over every tests/ answer and every bench proof. That did not fit this lane's build budget
and time after steps 1 and 2; it stays open as G-LG30-1.

## Gaps

| Id | Gap |
|---|---|
| G-LG30-1 | G-LG29-3 is unchanged: a `forall` without `trigger` still lets z3 pick its patterns. Rule as in G-LG29-3: when the program gives none, the verifier picks the slot read `a[c + j]` (`c` constant) of the bound variable as the pattern, in both compilers with the same trace; it lands only if no `tests/` answer and no bench proof flips. |
| G-LG30-2 | G-LG29-1 has no must_reject test: an unguarded W of a `str` read in an opaque body is never false while `str` values are valid by type (G-LG28-1). Rule: once G-LG28-1 gives a value whose W can fail on one path, add a must_reject that relies on the occurrence guard. |
| G-LG30-3 | The guard an opaque occurrence keeps does not include the range of an enclosing quantifier: the body of `forall i in lo..hi: ... F(x) ...` is evaluated under the outer guard before the range condition is built, so its facts (the W of a `str` read, inside opaque bodies and in quantifier bodies generally) are assumed even when the range is empty. Sound today (a `str` value is valid by type, G-LG28-1), and older than LG30. Rule: build the range condition first and evaluate the body under `guard && lo <= i && i < hi`, in both compilers with the same trace, together with G-LG30-2. |
