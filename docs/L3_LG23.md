# L3 LG23: `old` of element and length operands, struct invariants in payloads, LLVM `ok_val` of a legacy payload

Scope: G-LG22-2, G-LG22-1 and G-LG18-2 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is
changed. G-LG22-3, G-LG20-2/4/5, G-LG18-3, G-LG15-1, G-LG16-1 and G-LG21-x are out of scope and unchanged.

Status: LG23: G-LG22-2 partial (`old(a[i])`, `old(len(a))` and `old` of any field/index place chain or its `len` from an inout array or inout non-generic struct parameter, both compilers; `old` of an inout generic struct parameter is not reachable because such a parameter cannot be declared (type/inout_type), G-LG23-1)
Status: LG23: G-LG22-1 partial (invariants reached through generic struct fields, `Option` payloads, `Result<T, E>` Ok payloads and non-generic enum variant fields are assumed and checked as guarded clauses, both verifiers; array/Vec elements, Err payloads, generic enum variants and generic call sites remain, G-LG23-2, G-LG23-3, G-LG23-4)
Status: LG23: G-LG18-2 closed (LLVM `ok_val` of a `Result<Option<i64>, String>` / `Result<Result<i64>, String>` parameter in a runtime requires and a kept cost, both compilers, same results as the Rust backend)

## What landed

- More `old` operands (G-LG22-2). The operand of `old` may be a place chain, a root `p` followed by any `.field` and
  `[index]` steps (`a[i]`, `c.a[i]`, `c.s.n`), or `len` of such a chain of array type (`len(a)`, `len(c.a)`), where
  `p` is an inout parameter of array or non-generic struct type. The checker lowers it onto the existing
  whole-parameter snapshot: `old(a[i])` becomes `old(a)[i]`, `old(len(c.a))` becomes `len(old(c).a)`, so the verifier
  and both code generators see only whole-parameter `old` as before. Index expressions are read in the current state;
  they may not read an inout parameter or contain `old` (type/old_argument "the index of an old operand cannot read an
  inout parameter; write old(a)[old(b)[0]] explicitly"). Any other operand (`old(a[0] + 1)`, a scalar or non-inout
  root, calls other than `len`) stays type/old_argument with the old message.
- Struct invariants in more positions (G-LG22-1). The effective invariant walk goes through steps instead of plain
  struct fields only: fields of a plain struct or of a generic struct instance (type arguments substituted, label
  `b.v`), the `Option` payload (guard `is_some`, value `some_val`, label `o.some`), the Ok payload of a two-argument
  `Result` (guard `is_ok`, value `ok_val`, label `r.ok`), and each field of each variant of a non-generic enum (guard
  `is_variant`, value `variant_field`, label `s.V.f`). A clause reached under guards g1..gn is `!g1 || ... || !gn || C`;
  with no guard it is exactly the LG22 clause, so existing output is unchanged. The cycle guard and the memoized "has
  an invariant" check use the full type key (or the enum name). Every LG16/LG22 use of the effective set (entry
  assumption, inout exit check, result check, call-site check and assumption, the legacy and host-entry
  entry_signature rules) sees the new clauses. Generic struct, `Some`, `Ok` and variant constructors are not checked
  at construction; the next handoff checks them.
- LLVM `ok_val` of a legacy payload (G-LG18-2). In the LLVM contract evaluator an Ok type that is a legacy `Option`
  or one-argument `Result` is loaded from the payload slot and passed on as a legacy value, so `is_some(ok_val(r))`,
  `some_val(ok_val(r))`, `is_ok(ok_val(r))` and `ok_val(ok_val(r))` work in a runtime requires and a kept cost.
- `tests/must_reject/lg16_inv_nested` used an `Option` payload as the position that is not assumed; that payload now
  carries the invariant, so the ordinary function with that parameter is type/entry_signature (line 8) in legacy mode.
- SPEC.md: the `old` bullet, the struct invariant paragraph (section 6a), the `Result<T, String>` LLVM paragraph,
  the section 6 `old` paragraph and the R-6g "Not supported" line; section 6a notes that `Result<T, i64>` is
  the legacy `Result<T>` and its Ok payload is not walked.

## Gaps

| Id | Gap |
|---|---|
| G-LG23-1 | `old` of an inout generic struct parameter: such a parameter cannot be declared today (type/inout_type), so the `old` rule has nothing to apply to; allowing inout generic struct parameters is a separate change (codegen and the verifier's snapshot of an instantiated struct). |
| G-LG23-2 | Invariants of structs that are array or `Vec` elements are not assumed or checked. They need a quantified clause over the elements (and its instantiation at element reads and writes), which is a new encoding with its own cost on array-heavy programs. |
| G-LG23-3 | The Err payload of `Result<T, E>` and the variant fields of generic user enums are not walked, so an invariant struct there is neither assumed nor checked. The Err side needs a guard on `!is_ok` with an `err_val` value in both verifiers; generic enums need the type arguments substituted into variant fields. |
| G-LG23-4 | A call of a generic function at an instantiated type argument (`ignore::<R>(r)`, `ignore::<R>(Some::<R>(r))`) neither checks nor assumes the invariant of `R` (or of `R` inside a payload) at the call site; the generic body sees an abstract `T`. Present before LG23 (31e29930 also accepts `ignore::<R>(r)` with a broken `R`). Closing it needs the effective invariant instantiated at generic call sites and a rule for what a generic body may assume and must preserve. Found by the review. |
