# L3 DB45: grok one-pass line reader for ord and dense

Lane: bench/l3/grok/ (new module `line.pruv`, additive functions in `entry.pruv`, one call site in `read.pruv`).
Baseline: main 2e9f728f (docs/L3_DB43.md quiet rerun: ord M/L 1.94x/1.95x hand, dense M/L 1.45x/1.43x hand).

## 1. Design (G-DB43-2)

### Where the old path spends time

Per history line the old reader runs `parse::scan_into` (tape tokenizer over the whole line, UTF-8 checked byte by byte inside
strings), `access::view_root_type`, `lines::build_span` (owned copy of line + tape for user/assistant lines), then `entry::feed`
looks up each field by name over the tape and decodes the wanted strings through `jstr` (a second UTF-8 check), and the user_query
unwrap copies once more through `adapter_probe` (a third check). A dense `0` or `{}` line still pays the scratch tape setup.

### New path

`line::step(line: [u8], ...)` is called by `read::line_step` with `subview(win, lo, hi)` (a borrow, no copy). Flow per line:

| Flow | What happens | Cost bound |
|---|---|---|
| F0 first non-whitespace byte is not `{` | Every such line is a skip in the old path too (non-object root, or invalid JSON): return 0. | O(leading whitespace), no allocation |
| F1 `{` line | One left-to-right member scan: strings are scanned for `"`, `\`, control bytes and escapes; nested values are skipped by a recursive grammar check (`skip_value`, fallback deeper than 120); numbers/literals validated by the JSON grammar. Wanted top-level keys (raw byte compare, keys without escapes): `type`, `synthetic_reason`, `prompt_index`, `content`, `timestamp`, `created_at`, `tool_calls`; for each the value kind and byte span are recorded in a reused `[i64]` scratch, plus up to 64 content-part `text` spans and the tool_calls element count. | linear in line length, one pass; scratch reused across lines |
| F2 type is not "user"/"assistant" | return 0 after the scan (old path also skips). | (inside F1) |
| F3 user/assistant | One runtime `utf8_valid(line)` (lowers to `core::str::from_utf8`; only these lines pay it, failure falls back). A single escape-free content span is passed borrowed as `subview(line, a, b)` without a copy; otherwise decode only the recorded content spans into one `String`: escape-free runs are pushed as `subview(line, a, b)` str pieces (both ends next to ASCII bytes, so char-boundary facts come from the runtime-checked `utf8_valid(line)` and the boundary bytes), simple escapes push a literal. Timestamp (`timestamp`, or `created_at` when it is null/absent): a 24-byte escape-free string with ASCII bytes at both ends is checked with `time::canonical_iso` on a borrowed str; numbers and other strings fall back. `push` keeps the `string_push_str` length precondition as a runtime check. Then the same decision code as `entry::feed_user` / `feed_assistant` runs on the decoded values (shared, not copied). | linear in content length (each content byte read once more, copied once into the result String) |
| F4 anything outside the fast scope | line longer than 1 MiB (the old parser's tape record limit could reject it), `\u` or `\b`/`\f` escape in content, any `\u` or bad escape in the line, escaped key or type, duplicate wanted key, more than 64 parts, depth > 120, invalid UTF-8 on a user/assistant line, non-canonical non-null timestamp/created_at (numbers, odd strings), any grammar doubt: return "fallback" and `read::line_step` runs the old tape path unchanged on the same span. | old cost + at most one aborted scan (linear) |

Equality with the old reader is by construction: the fast path only answers lines whose result it can decide with the same rules
(JSON validity, object root, field kinds, decoded content, canonical timestamp), everything else goes to the old code. Behavior
differences that remain are recorded as D-DB45-n.

Proof obligations stay in Pruv: all index bounds proved (loop invariants on the scan cursor), the `str` pieces are borrowed with
`subview` (R-6g-10) from the runtime UTF-8 fact plus char-boundary facts; no new unchecked conversions. The collector contract
(`turns::begin2`/`answer2`/`tool`) is unchanged.

Memory: no per-line owned copy of the line or the tape (old path copies both for every user/assistant line), so RSS should not
grow; the content String is the only per-line allocation (the old path allocates it too).

### Alternative considered: keep the tape and fix it there

Keep `scan_into` + tape, remove the owned `build_span` copy (tape access over the borrowed window), drop the second and third
UTF-8 checks, early-out dense lines before the tape. Expected to recover the copy and double-check cost (DB43 gen.rs measured
UTF-8 double check ~15%, adapter copy ~0%), but the tape write per token and by-name field search over the tape remain.

## 2. Debate

One debate delegation (Codex gpt-6.2-astra, ultra effort) judged design A (one-pass reader over the borrowed line) against B (keep
the tape and fix it there: borrowed tape access, no second/third UTF-8 check, dense early-out). It was given the DB43 numbers and
both designs, but not my preference.

Outcome: A is more likely to reach hand 1.0x on both shapes; B has the lower risk of changing behavior. Its argument against B:
even if the measured ~15% double UTF-8 check is all recovered, ord is `1.94 x 0.85 = 1.65x`, because every token is still
written to the tape and fields are then searched by name over the tape. Risks it listed for A: (1) accepting invalid JSON that a
depth counter alone would miss (`[{]}`, missing commas), (2) field equality (text before type, escaped keys equal to plain keys,
duplicates, odd timestamps), (3) char boundaries of borrowed pieces and escape decoding, (4) double cost when a long line falls
back late, (5) per-line scratch setup and result-String reallocation.

Decision: A, with B's safety kept as the fallback. Every line the fast path cannot decide with the old rules returns 3 and the
unchanged tape path runs on the same span, so B's "same tokenizer" guarantee holds for everything outside the fast scope. Answers to
the risks: (1) `skip_value` is a recursive grammar check (objects, arrays, commas, colons, numbers, literals), not a depth
counter; (2) escaped keys and duplicate wanted keys fall back, member order does not matter (spans are recorded first, decided
after the scan); (3) every borrowed piece has a runtime check that its ends sit on ASCII or lead bytes after `utf8_valid`, so the
`subview` str conversion is proved, not trusted; (4) measured below: no gate row falls back; (5) scratch is the reader's existing
256-slot tape buffer (34 slots reset per line), dense lines `0` stop at the first byte.

## 3. Behavior

Implemented as a new module `bench/l3/grok/line.pruv` plus `entry::user_view` / `entry::assistant_view` (same decision code as
`feed_user` / `feed_assistant`, taking a borrowed `str` content); old functions are unchanged and still used for the fallback.
`read::line_step` calls `line::step` first when the scratch is at least 256 slots.

Audit (Codex gpt-6.2-astra, ultra): one must-fix. A valid line over 1 MiB with more than 1,048,576 JSON values (e.g. a long
`pad` array of `0`s) is rejected by the old parser's record limit (skip), while the fast scan accepted it and opened a user turn.
`read::window` frames at most 1 MiB per line, so the reader never reached it, but `line_step` itself accepts up to 16 MiB. Fixed by
falling back for lines longer than 1 MiB (each record starts at a distinct byte, so shorter lines cannot exceed the limit);
recheck in section 6. No other difference was found (whitespace, numbers, literals, trailing commas, nesting, duplicate keys,
member order, part joining, tool_calls count, synthetic_reason/prompt_index order, timestamp precedence and range, escapes,
char boundaries, state on fallback).

After the fix no behavior difference is known: all fast-path decisions replicate the old rules and everything else falls back. No D-DB45-n row.

## 4. Time and memory (rs/rust)

10 rounds, alternating old (main 2e9f728f) / new / hand per round with rotated order, `exe time impl path 300`, median of the
per-round medians; RSS is the median of 3 `/usr/bin/time -l` runs. Same machine, load average 7.06-8.36 (1-minute, sampled per
round). Checksums of old, new and hand agree on every cell.

| Cell | old ns | new ns | hand ns | old/hand | new/hand | RSS old | RSS new | RSS hand |
|---|---|---|---|---|---|---|---|---|
| ord M (hist-ord-2m) | 7459531 | 5900646 | 3716676 | 2.01x | 1.59x | 23937024 | 23134208 | 20250624 |
| ord L (hist-ord-8m) | 30792562 | 22668802 | 14405208 | 2.14x | 1.57x | 43892736 | 43237376 | 33275904 |
| dense M (hist-dense-2m) | 6654489 | 3155781 | 4410917 | 1.51x | 0.72x | 4145152 | 4079616 | 3915776 |
| dense L (hist-dense-8m) | 28046292 | 12987708 | 18305885 | 1.53x | 0.71x | 10518528 | 10403840 | 10240000 |

RSS split (fixed = M minus slope x M bytes; slope = RSS growth per input byte between M and L):

| Shape | old fixed / slope | new fixed / slope | hand fixed / slope |
|---|---|---|---|
| ord | 16.5 MiB / 3.17 B/B | 15.7 MiB / 3.20 B/B | 15.2 MiB / 2.07 B/B |
| dense | 1.9 MiB / 1.01 B/B | 1.9 MiB / 1.01 B/B | 1.7 MiB / 1.01 B/B |

Dense meets the goal (time 0.71x-0.72x hand, RSS within 0.2 MiB of hand and below old). Ord improves from 2.0x to 1.6x and
its RSS is below old, but neither time nor the proportional RSS reaches hand (G-DB45-1, G-DB45-2).

Ord breakdown (ord-8m, experimental copies of the generated Rust, load ~10): full 20.5 ms; scan + `utf8_valid` only 12.0 ms (hand
total 13.4 ms); without `go`/collector 18.6 ms. So content decode is ~6.5 ms and the collector ~2 ms. The decode cost is two
passes over the content (scan, then decode) plus many short `string_push_str` calls (ord content has frequent `\"` and `\n`)
into a fresh `String` per line that grows by reallocation; hand decodes during the single parse into one reused `Vec`. Dropping
the `string_to_str` clone made no measurable difference.
