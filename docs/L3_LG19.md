# L3 LG19: owned `?` temporaries with plain arguments only, isolated rs solver checks, `count` range split

Scope: G-LG18-4, G-DB29-1 and R03L-G2. Both compilers (Python `pruvc/`, Rust `pruvc-rs/`) where the item has a
Python side. No `bench/` file is changed. G-LG18-1/2/3, G-LG15-1 and G-LG16-1 are out of scope and unchanged.

Status: LG19: G-LG18-4 closed (an owned temporary for a take parameter is lifted only when every argument of the lifted call is a value, a place or a move; otherwise type/try_position, both compilers)
Status: LG19: G-DB29-1 closed (the rs verifier checks each query in a fresh Z3 context made by Z3_translate, so datatypes declared for other queries no longer perturb the search; the a4 dummy-datatype repro times out before and verifies after; cost G-LG19-2)
Status: LG19: R03L-G2 closed (built-in count range split lemma F(x,y) == F(x,m) + F(m,y) for x <= m <= y in both verifiers, SPEC.md R-6-4; it does not unblock G-DB30-1, which stays blocked by G-R03D-1)

## What landed

- Plain arguments for owned temporaries (G-LG18-4). In `try_owned_temp` (Python) and the owned branch of
  `try_temps` (Rust) the lifted call result is bound only when every argument of that call, recursively through the
  argument's own sub-expressions, is a `move`, an integer or bool literal, a place whose root is a local (`x`, `x.f`,
  `x[i]`), or a unary / binary / index operator over such operands. The check is syntactic: it does not type-check
  the argument again, so a rejected argument keeps the `try_position` diagnostic instead of a standalone type error.
  A string literal and any call are not plain: `mk(string_from("a"))`, `mk(len("a"))` and
  `mk(vec_get::<String>(v, 0))` build or borrow a value that the temporary's `let` would drop before the `?` operand
  runs, so they stay `type/try_position`, as on main before LG18. A place, an int or bool literal and a move create
  no value the `let` could drop early, so the lifted statement has the same drops in the same order as the unlowered
  one. Calls whose result is a value type (`mk(len(s))`) are rejected too; that is conservative, not a regression
  (main rejected every owned temporary, G-LG19-3).
- Isolated solver checks (G-DB29-1, rs only). `Solver::check` in `pruv-proof/src/sys.rs` builds a new context with
  the same timeout, rlimit and seed, translates every assertion into it with `Z3_translate` and checks there; the
  model is translated back with `Z3_model_translate`, `reason_unknown` reads the isolated solver. The shared context
  holds every datatype the module declares; with the check in its own context only the sorts the query reaches are
  declared, so an unused datatype no longer changes the search. Python builds every datatype in one context too, but
  showed no such timeout; it is unchanged.
- `count` range split (R03L-G2). For each `count` aggregate function `F(lo, hi, outer...)` both verifiers add, next
  to the empty-range and one-step lemmas, `forall x m y. x <= m <= y ==> F(x,y) == F(x,m) + F(m,y)` with the
  multipatterns `{F(x,m), F(m,y)}`, `{F(x,y), F(x,m)}` and `{F(x,y), F(m,y)}`. Every pattern pair binds all three
  variables from terms that already exist, and an instance only creates terms over existing endpoints, so it adds no
  matching loop. Python asserts the split only in a third attempt, after the query without lemmas and the query with
  the other aggregate lemmas are both not unsat: with the split in the second attempt, `bench/l3/claude` a0 timed out
  in `boundary::copy_span` (a function with no `count`; 19 s and verified without the split, `verify_unknown` with
  it). Rust asserts it with the other lemmas; its isolated check verified a0 (G-LG19-4). SPEC.md R-6-4 states the rule and links `tests/spec/r6_4_count_split.pruv` (accept: join and rest of
  two adjacent counts) and `tests/spec/r6_4_count_split_unbounded.pruv` (reject: the split point is not inside the
  range, `verify/ensures`).
- G-DB30-1 stays open. Its `refresh_turn_tail` proof needs the count of a range to survive an `inout` call that does
  not touch it, which is the missing frame lemma of G-R03D-1, not a split. The split lemma is sound and needed once
  the frame is known, but alone it does not close the proof.

## Gaps

| Id | Gap |
|---|---|
| G-LG19-1 | A value-type temporary lifted before `?` can still move a drop: `lend(mk(2), 0) + need(x)?` binds `lend(...)`, whose own argument `mk(2)` (a non-value) is dropped at the end of the `let`, before `need(x)` runs. Pre-existing since LG14 (value temporaries are not covered by the G-LG18-4 rule); the same plain-argument check would close it. |
| G-LG19-2 | The isolated rs check translates every assertion per query: a4 base verification went from 45.85 s to 59.37 s (about 30% slower). Small queries pay more: `tests/must_reject/g10a_v_wait_equal` takes 4 s instead of under 1 s, and in the full rs `run_all` (run next to two other test jobs) it gave `verify_unknown` instead of `assert`; alone it gives `assert`. Caching the translated prefix per solver or translating only on retry after `unknown` would recover it. |
| G-LG19-3 | The plain-argument rule rejects any call inside the lifted call's arguments, also when its result is a value type and its own arguments are plain (`eat(mk(len(s)), need(x)?)`). Accepting those needs the argument's type at this point without a second type check; until then such code keeps `type/try_position`, as on main. |
| G-LG19-4 | The two verifiers stage the count split differently: Python adds it in a third attempt only, Rust with the other aggregate lemmas in the second. No build was left to stage it in Rust too; rs a0-a4 verify as is. Why the split slows a Python query that has no `count` term in its goal (`boundary::copy_span`) is not analyzed. |
