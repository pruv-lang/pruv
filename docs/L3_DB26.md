# L3 DB26: codex reader buffers and pkgs/turns store

Base: main bd9a45bd. Survey: docs/L3_DB5.md, docs/L3_DB11.md and docs/L3_DB19.md (not repeated here).

## 1. Measure first (D-DB11-2)

`measure_r09.py`, 7 alternating rounds on base (load 12-15), then a heap profile of one L read with a counting
allocator (allocations of 16000 bytes and up, `/tmp`, not committed). The base L read peaks at 6.72 MB of live heap, in
this order:

- `hb` (`util::grow_bytes` doubling): 262144 -> 524288 -> 1048576.
- The `pkgs/turns` store (`reserve` doubling): 266648 -> 533332 -> 1066768.
- `finish2` text 929384, then `copy(text)` into `Collected` 945570, then the wire 962783.
- Host `render_read`: per-turn `String`s, `join`, then `format!` and push, which reallocates 56 -> 962793 -> 1925586.

The M read peaks at 1.69 MB, mostly about 18 page-line buffers and copies of about 50 KB, a 240 KB host doubling, `hb` at
262144 and the store at 266648. On top of the heap, macOS RSS counts every page touched over the 20-read batch.

## 2. Changes

- `codex/read.pruv` `replay` (D-R09-1): the store is built once at its final size. A loop over the held turns sums
  each turn's clipped prompt (at most 32768) and clipped reply plus the 4-byte pad (at most 32768), and
  `Store.data` is `alloc(need, 0)`. The invariant `0 <= need <= 65536 * h` proves the size is in range. `reserve`
  then never grows or repacks it. This is a capacity change: the layout (`data`, `off`, `stamp`, `end`) is unchanged.
- `pkgs/turns/turns.pruv` `finish2`: both `Collected` returns move `turns` and `text` instead of copying them. This removes one
  text-sized copy per read. The old `finish` is unchanged.
- `codex/host/src/lib.rs` `render_read` (host I/O only): it writes into one `String` presized from the text
  (`text.len() + text.len()/16 + 160*kept + 1024`) instead of per-turn strings, `join` and `format!`. The output bytes
  are the same.
- `hb` (D-R09-2) is not presized. Its size is known only after the last page arrives, and it already doubles
  (`util::grow_bytes`, DB5).
- D-DB11-1 was attempted and reverted. It added `plan` ensures and loop invariants that state
  `pre[j+1] == pre[j] + plen + rlen + 24*cp + 24*dp` for the planned slots, plus `finish2` loop invariants over `p`, so
  the run-time check in `finish2` could go. z3 returned unknown (timeout) on the `plan` loop invariant and on three
  `copy_span` preconditions in `finish2`, after a 4.5-minute verify. The run-time checks in `begin2`/`answer2`/`finish2`
  stay (G-DB26-1).

## 3b. Audit

None. No new proof landed. The store change sizes `alloc` from a bounded sum and keeps the layout. The `finish2` change is
`copy` -> `move` on values that are not used afterwards. The brief asks for an audit only for a new proof, encoding or
store layout.
