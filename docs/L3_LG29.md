## Step 1: why `plan_end` was fragile (G-LG28-6)

`plan_end` writes one slot (`sl[1600 + i] = end`) and proves `planned_spans(sl, b, i + 1, end)` from
`planned_spans(sl, b, i, prior)`. The second `forall` of `planned_spans` has no trigger, so z3 picks its own
patterns among the row reads `sl[8 * ((b - 1 - j) % 200) + c]`. Every match instantiates the clause with a new
`(b - 1 - j) % 200` term, and the integer core then searches over them: on a failing seed the dumped query shows
about 37k instantiations (3k on a passing one), 4475 rows in the arithmetic tableau, Gomory cuts and dio calls.
The run is context sensitive (G-R08-2): the base Python and the LG28 Python emit the same query in two equivalent
forms, and the LG28 form fails 1 of 8 seeds and passes the others near the 8 s limit. That is the a2 flip of LG28.

The fix uses an existing language feature, `forall ... trigger t:` (SPEC R-6-3), which changes only
instantiation, never meaning, and adds no generated code. Tried first and rejected (seed counts on the base
standalone query unless noted):

| Variant | Result |
|---|---|
| base (no change) | 26 of 30, max 6.28 s; LG28 form 7 of 8, max 7.99 s |
| split the `ensures` into its conjuncts | no gain: each `ensures` is its own query and earlier ones are not assumed |
| body `assert`s of the old and new facts | worse: more quantified hypotheses, more instances |
| one `forall` holding both clauses | worse, 8 of 12 |
| trigger `sl[1600 + j]` in `planned_spans` itself | `plan_end` 20 of 20 at 0.00 s, but `plan` times out (call `requires`, loop invariant, `ensures`): after the loop havoc `sl` is an `ite` over the havoc array, so no ground term matches the pattern and the hypothesis is never instantiated |
| that pred for both `requires` and `ensures` of `plan_end` | `plan` loop invariant `planned_spans` times out on the triggered callee `ensures` |
| that pred for `plan_end`'s `requires` only (landed) | `plan_end` `ensures` 20 of 20 at 0.01 s on the LG28 form; `plan` and `write_turns` unchanged |

A trigger matters only where the formula is assumed. In `plan_end` the `requires` is the hypothesis that blew
up; at the call site in `plan` it is a goal (negated and skolemized, so its trigger is unused), and the
untriggered `ensures` gives `plan` the same hypothesis as before. `planned_spans_slot` is a private `pred fn`
with the same body plus triggers, so the contract means the same and the generated Rust is byte-identical.

The `plan` sum invariant (turns.pruv:425, `total == sum(...)`) still needs the third proof attempt (split lemmas)
in every Python run, base included (two 8 s timeouts, then unsat); it is not new and not changed here (G-LG29-2).

## Step 2: G-LG28-5 stops

`opq_body` evaluates the opaque body with an empty guard in two places: when an application is unfolded at once
and when `reveal` adds the equation of every application met earlier on the path. Pushing the body's W facts
under the caller's guard needs that guard per application: `st.apps` stores `(f, app, args)` only, and `reveal`
runs later under its own path guard, not the one of the call site. Keeping a guard per application (and both
compilers agreeing on it in the trace) is a new analysis, so by the stop rule it is G-LG29-1, with no code.

## Gaps

| Id | Gap |
|---|---|
| G-LG29-1 | G-LG28-5 needs the call-site guard of each opaque application: `st.apps` (`pruvc/verify.py`, `symbolic.rs`) keeps `(f, app, args)` and `reveal` adds the equation later under its own guard. Rule: store the path guard with each application, keep the definition equation `app == body` unguarded, and add the W facts the body evaluation pushes under the stored guard, in both compilers with the same trace; land with a must_reject test once G-LG28-1 allows one. |
| G-LG29-2 | `turns::plan` sum invariant (bench/l3/claude/turns.pruv:425) times out on the first two Python proof attempts in every a2 run and is proved by the split-lemma attempt; base does the same. Not a flip today, but the same kind of context-sensitive margin as G-LG28-6. Rule: when a2 time matters, add a per-step hint (`assert` of the one-step sum unfolding) in the loop body and keep it only if a2 verifies 3 of 3 on Python and rs with no fallback. |
| G-LG29-3 | The root cause of G-LG28-6 is language level: a `forall` without `trigger` lets z3 pick arithmetic-heavy patterns, and a trigger in a `pred fn` stops working where the array is a havoc `ite`. Rule: the verifier picks the slot read (`a[c + j]`, `c` constant) of the bound variable as the pattern when the program gives none, in both compilers with the same trace, and lands only if no `tests/` answer and no bench proof flips. |
| G-LG29-4 | bench/l3/codex `read_server_requests` is flaky on Python and rs, both backends: the child's last log line (the "not handled" reply to request 6) is sometimes missing, so the request log differs from TS. This lane's generated code does not change (byte-identical outputs), and the bench is outside this lane; not checked at 7552b1d9. Rule: the bench's log read waits for the child to exit (or the runner flushes before it closes the pipe), owned by the codex bench lane. |
