# L3 DB48: grok ord proportional RSS in the turns store (G-DB45-2)

Brief: find where grok's ord rows get their 3.20 B/B proportional RSS (hand 2.07 B/B, DB45) and cut it inside
`bench/l3/pkgs/turns/` without changing signatures other packages call; ord and dense proportional RSS at or under
hand, time not worse. Then, only if time is left, the part of the codex `hb` doubling chain (G-DB40-1 / G-DB46-3)
that lies in `pkgs/turns` or `bench/l3/codex`. Base: main 9a6e2473. The rs compiler was built once from this base
(release `pruvc`); no other compiler build. main 4b58af26 (DB47, grok only) was merged in before the last
measurement and the grok / opencode test_impl runs.

## What landed

- `bench/l3/pkgs/turns/turns.pruv`, `reserve` (the Store grow path): the new buffer is still `2 * tgt` (at least
  65,536 bytes), but when that is past 1 MiB it is 4,259,840 bytes instead. `live <= 2097152` and `need <= 32768`,
  so `tgt <= 2129920` and a 4,259,840-byte buffer always takes the in-place branch (`tgt <= len - tgt`) on every
  later grow. No signature, contract or caller changed; the Store header comment says the same.

## G-DB45-2 cause

Measured with a counting global allocator linked into the perf driver (scratch, logs every allocation of 128 KiB or
more). The heap peak (input window excluded) was close to hand: L 23.22 MB vs hand 23.08 MB, M 18.02 vs 16.21. The
RSS gap at L (about 10 MB) was allocation churn in the Store's data buffer, not live bytes: the doubling chain
136,542 -> 279,862 -> 561,160 -> 1,126,086 -> 2,253,718 -> 4,171,540, then two more fresh 4.17-4.19 MB buffers,
because once about 2 MiB of records is live a grow needs `tgt > len / 2` and so a new buffer of `2 * tgt` instead of
packing in place. 35.9 MB of zeroed allocations for a 23.2 MB peak; the freed blocks stayed resident. Hand has one
16.7 MB packet allocation and a ring of small per-turn Vecs. Dense rows never grow the Store past 196,608 bytes, so
they had no slope to cut (1.02 B/B against hand 1.00).

With the change the L chain is 136 K -> 279 K -> 561 K -> 4.26 MB (zeroed; pages are touched only as records are
written), then in place. Small windows (under 512 KiB of live text) keep plain doubling, so the 64 KiB row and the
dense rows never map the large buffer; a first version that always allocated 4,259,840 bytes made the 64 KiB row
29% slower and dense RSS 0.03-0.09 MB higher, and was dropped.

## Decisions

| id | decision | why | status |
|---|---|---|---|
| D-DB48-1 | `reserve` jumps to the 4,259,840-byte bound once a grow would pass 1 MiB, and keeps doubling below that | the bound (2 x (2 MiB live + 32 KiB need)) is the smallest buffer that never needs another allocation; below 1 MiB doubling keeps small windows from mapping it | kept |
| D-DB48-2 | the codex `hb` step of the brief was not started | codex does not use the turns Store (only qwen and grok do), so the turns change does not touch codex cells; an `hb` change needs its own codex test_impl run (about 40 min) and measurement, which did not fit the 1h45m cap | G-DB48-3 | G-DB47-1 (ord M 1.04x hand) is not in `turns` | `new_slots` (12,800 B) and `new_store` (200 x 8 + 9,600 B) are small allocations; a `sample` profile on ord M (DB47 grok) shows the zeroing cost as `__bzero` under `malloc_large_huge`: one cluster of 82-85 samples in both old and new (about 4.5% of the window; most likely the 1,730,425-word `[i64]` packet that `read::assemble` allocates zeroed, where hand uses `Vec::with_capacity`), and one of 10 (old) / 32 (new) samples for the Store buffers. The packet allocation is in `bench/l3/grok`, outside this lane | grok lane: fill the packet without a zeroed allocation (for example build it with pushes into a reserved buffer), then re-profile ord M |
| G-DB48-4 | grok and opencode test_impl did not finish before the commit | the four test runs were chained in one 75 min command and took 54 min for codex alone under load 9-41; the cap left no time to rerun | run grok and opencode test_impl on all four pairs on this commit |
