# L3 DB21: ord decode plain-string path, build_span copy, transport receive_grow

Base: main be2f3485. Survey: docs/L3_DB15.md and docs/L3_DB19.md (not repeated here).

## 1. Changes

- `lines::build_span` (D-DB15-3): the span bytes are built with `copy(subview(data, lo, hi))` (one allocate-and-fill)
  instead of a zeroed `alloc` plus a byte loop. The tape prefix keeps its loop (G-DB21-1).
- Plain-string mark (D-DB15-1): `parse::scan_into` writes slot 5 = 1 on a kind 4 (string) or 7 (key) record whose token
  had no backslash (`Token.plain`). `scan` and `scan_document` still write 0, and their contracts say so. `json::rec_ok` /
  `check_tape` accept slot 5 in {0, 1}, with 1 only on kinds 4 and 7. `access::string_text_scanned` takes
  `jstr::string_text_plain` on a marked record: the bytes are copied once (`alloc` plus `copy_range`), with no
  count-and-decode pass. The mark is a run-time fact with no type link to the source (G-DB21-2).
- grok `rpc.pruv` `aux` (D-DB19-1): it starts at 512 bytes, not 8389120. `on_reply` grows it with `transport::grow_line`
  when the raw error code reaches the end. `failure()` and `load_check` are bounded by `len(aux) - 512`.
- mcp `root.pruv` (D-DB19-2): the line buffer starts at 4096 and goes through `transport::receive_grow` with cap 4194304.
  `transport::receive` is removed (mcp was its last caller). `grow_line` requires `cap <= 8389120` (for grok `aux`).
- codex (D-DB19-2): the move to `receive_grow` was written and then reverted. On py/llvm, `read_server_requests` lost
  the reply to the second server request (id 6) in a batch with the request, a notification and the result. It failed
  twice on this tree and passed on base be2f3485 with the same compiler (G-DB21-3). codex keeps its own `receive`. Only
  the header comment changed (it pointed at the removed `transport::receive`).

| id | what | status |
|---|---|---|
| D-DB21-1 | Time of ord and dense against base is unmeasured: 8 rounds at load 6-26, below the 15 the brief asks above load 16. Rerun 15 alternating rounds on a quiet machine before D-DB15-1 can close. | open |

| G-DB21-1 | `copy(subview(tape, 0, m))` on an `[i64]` in `build_span`, in a `let` or a struct field, fails verification with "z3 error 6: invalid pattern". `copy(subview(data, lo, hi))` on `[u8]` works. So the tape prefix of a span document is still a zeroed `alloc` plus an element loop. | open |
| G-DB21-2 | The plain-string mark in tape slot 5 is set by `scan_into` and trusted by `access` at run time. `check_tape` only checks that it is 0 or 1 on kinds 4 and 7. Nothing in the type of `JsonDocument` ties the mark to "the source span has no backslash", so a hand-built tape with a wrong mark would return the raw escaped bytes. The language would need a refinement or ghost fact on tape records tied to `source`. | open |
| G-DB21-3 | codex on `transport::receive_grow` fails `read_server_requests` on py/llvm only (py/rust passes, and base passes on both). The reply to the second server request in one read is missing from the request log. The cause is not isolated. A likely suspect is `inout line.data` (a struct field passed `inout` and reassigned by `grow_line`) on the llvm backend, since grok and mcp pass a plain `[u8]`. | open |
| G-DB21-4 | `JsonDocument` owns `source: [u8]` and cannot hold a view of the caller's buffer, so a span document always copies its bytes. That copy is the remaining ord RSS over hand (D-DB15-3). A document type with a borrowed source would need a lifetime or region on struct fields. | open |
