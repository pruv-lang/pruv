# L3 DB52: codex per-read RSS attributed; in-place `grow_bytes` tried and reverted (G-DB50-2, G-DB50-3, G-DB46-3, G-DB44-2)

Brief: attribute the bytes of one L read (G-DB50-2) and the growth from 1 to 20 reads per process (G-DB50-3) by
tracing the allocations of the generated rs/rust program, without changing the compiler; then cut inside
`bench/l3/codex` (buffer sizes, reuse across reads, dropping a copy) only where every codex gate cell (M and L)
keeps RSS at or under its current value and time does not get worse. Fixes that belong to the compiler, runtime,
`bench/l3/lib` or `bench/l3/pkgs` are written as G-DB52-n. Base: main a8ba5771.

## Result: attributed; the one in-lane cut was tried and reverted

`bench/l3/codex` is unchanged on this branch; only this document is committed. The cut below verified on all four
pairs and cut RSS and time on both Rust-backend pairs, but rs/llvm L RSS rose over its base in both 10-round runs
(+377 KB and +66 KB), so it fails the gate "every codex gate cell at or under its current value" and was reverted
(D-DB52-1, G-DB52-4).

## Tried: `grow_bytes` takes the buffer `inout` (D-DB52-1)

`crate::util::grow_bytes` was `fn grow_bytes(buf: [u8], needed, cap) -> [u8]` returning `resize(buf, next, 0)`.
A borrowed parameter returning `resize` is emitted as `Vec::with_capacity(next)` + `extend_from_slice(buf)` +
fill: a fresh block next to the old one, both live while the prefix is copied. It now is
`fn grow_bytes(inout buf: [u8], needed, cap) -> ()` with `buf = resize(buf, next, 0)`, which SPEC.md "resize in
place" (an `inout` resizable array reassigned from `resize` of itself) emits as `Vec::resize` on the caller's
`Vec` (one `realloc`). The two call sites pass the field place (`inout hb.data` in `read::absorb`,
`inout line.data` in `rpc::receive`, SPEC field places LG6). Contracts are unchanged in content (`needed <= len`,
`len <= cap`, prefix kept as `old(buf)`). Three files: `util.pruv`, `read.pruv`, `rpc.pruv`; the whole diff:

```
-pub fn grow_bytes(buf: [u8], needed: i64, cap: i64) -> [u8] ! alloc
+pub fn grow_bytes(inout buf: [u8], needed: i64, cap: i64) -> () ! alloc
   requires len(buf) < needed && needed <= cap && cap <= 8700000
-  ensures needed <= len(result) && len(result) <= cap
-  ensures forall k in 0..len(buf): result[k] == buf[k]
+  ensures needed <= len(buf) && len(buf) <= cap
+  ensures forall k in 0..len(old(buf)): buf[k] == old(buf)[k]
 {
   ...
-  return resize(buf, next, 0);
+  buf = resize(buf, next, 0);
 }
 read.pruv absorb:   hb.data = crate::util::grow_bytes(hb.data, needed, 8700000)   ->  crate::util::grow_bytes(inout hb.data, needed, 8700000)
 rpc.pruv receive:   line.data = crate::util::grow_bytes(line.data, needed, 8388608) ->  crate::util::grow_bytes(inout line.data, needed, 8388608)
```

Checks of the tried change: pruvc-rs verified it (`{"ok": true}`, 736 s); `test_impl.py` (full verify, all four
pairs) 136/136 on py/llvm, rs/rust, rs/llvm and 135/136 on py/rust with `read_server_requests` failing (G-DB32-2);
that case alone three times: py/rust 3/3; rs/llvm failed once of three (the same known timing flake), every other
pair 3/3. Base (a8ba5771) `test_impl.py --reuse-verified`: 136/136 on all four pairs.

## Method

A counting global allocator (`#[global_allocator]` wrapping `System`, keyed by a 22-frame raw backtrace, no frame
skipped so inlined frames resolve) was linked into the test_impl harness of the rs/rust emission and into the hand
reader. A per-read mark dumps, per site: bytes allocated, count, bytes live at that read's peak, bytes live after
the read, largest block. Addresses were resolved with `atos -i` (inline chains) and grouped by the first frames
outside `std`/`alloc`/`core`. Every traced run's stdout was compared with the hand reader's stdout for the same
input (all matched). The tracer is scratch (`/tmp`, deleted); nothing in it is committed.

## G-DB50-3: M, 20 reads in one process

| read | old peak live | new peak live | hand peak live | live after read (old / new / hand) |
|---|---|---|---|---|
| 1 | 809,084 | 779,653 | 424,192 | 10,940 / 10,940 / 18,148 |
| 2 | 809,084 | 714,117 | 424,192 | same |
| 3 | 904,411 | 684,326 | 424,192 | same |
| 10 | 904,411 | 684,326 | 424,192 | same |
| 20 | 773,339 | 684,326 | 424,192 | same |

Nothing stays live between reads: after every read the Pruv heap is back to 10,940 bytes (hand: 18,148), and
neither side caches anything across reads. The growth from 1 to 20 reads is therefore allocator retention, not
program state: each Pruv read allocates and frees about 2.6 MB in 1,053 blocks (hand: 1.6 MB in 3,171 blocks), of
which the large ones (`hb` 64 -> 128 -> 256 KiB, `chunk` 64 KiB, the runtime reader queue 64 KiB, three copies of
the 50 KB line, `fb` 32 KiB, `pb` 18 KiB) are new zeroed blocks every read. Freed medium blocks stay resident in
libmalloc's caches, and a reused zeroed block is cleared with `bzero` (DB50), so each read can land its large
blocks on different pages than the last. Hand's only large block is its 64 KiB line buffer.

In place growth removes the 2-block peak of the `hb` chain (old peak live varied 773-904 KB from read to read; new
settles at 684 KB) but the M growth (new 1.66 MB, old 1.64 MB on the scratch runners) did not shrink:
the per-read fresh large blocks are the cause, and keeping them across reads needs state that outlives one
`codex_read_wire` call (G-DB52-3).
