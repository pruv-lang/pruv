# L3 DB19: grok RPC line buffer grown to the line; DB15 tests finished on the final tree

Base: 08650b51.

## Result

- The grok ACP reader no longer allocates a fixed 8 MiB `line` buffer. It starts at 4096 bytes and doubles up to the
  8388608 cap, but only when a line needs the next byte. The framing, the `-3` "line too long" at the cap and the `st[]`
  protocol are unchanged.
- The brief asked for `inout line: Vec<u8>`. That type does not exist in the language (G-DB19-1), so the new reader uses
  a `[u8]` that is replaced by a longer copy.
- All outputs are unchanged (tests below).
- Peak RSS does not change measurably (section "Perf"). The old 8 MiB `alloc(n, 0)` was zero pages that were never
  touched, so it was virtual size, not resident memory.
- D-DB15-4 is partial: the solo `q.py` run is done and explained; `q_mutants.py` has M01-M04 killed, M05-M16 not yet
  recorded (section "Tests").

## What changed

`bench/l3/pkgs/transport/transport.pruv` (additive; `receive` and its callers in codex and mcp are untouched):

- `grow_line(line, cap)` returns a copy that is twice as long, at most `cap`, with the first `len(line)` bytes kept
  (`copy_range`).
  - requires `1 <= len(line) < cap <= 8388608`
  - ensures `len(line) < len(result) <= cap`
- `receive_grow` is `receive` with `len(line) == cap` relaxed to `1 <= len(line) <= cap` and `st[1] <= len(line)`
  (requires, ensures and the byte loop invariant).
  - The byte loop checks `st[1] == cap` (`-3`) before it grows, so `-3` is reported at the same byte as before.
  - A line grows only when `st[1] == len(line)`, and then by `grow_line`.

`bench/l3/grok/rpc.pruv`:

- `step` calls `receive_grow`.
- `step`, `pump` and `drain`: `len(line) == 8388608` becomes `1 <= len(line) <= 8388608 && st[1] <= len(line)` in the
  contracts and loop invariants. `step` also ensures `ctl[6] <= len(line)`, because `parse_line(line, ctl[6])` needs
  `n <= len(line)`.
- In `step`, the run-time guard `n <= 8388608` becomes `n <= len(line)`. It is still a run-time check, so no proof
  invariant replaces a run-time check, and no audit was run (brief rule).
- `load_check` starts with `alloc(4096, 0)`.
- `aux` (8389120 bytes, detail and raw error code) is still a fixed buffer (D-DB19-1).

- No `run_perf.py` row covers the RPC reader: the rows are history `read::window` only. The table below is therefore

Reading:

- The difference is within run-to-run noise. py/llvm `acp-load-ok` after is about 0.4 MB higher, which is less than one
  doubling step of the buffer.
- Before, the 8 MiB `alloc(8388608, 0)` was never written past the line length. The pages stay untouched zero pages, so
  they were not resident, and replacing them gives no RSS change.
- What does change:
  - The reader no longer reserves 8 MiB of address space up front.
  - A long line now costs the copies of the doublings: 12 steps from 4096 to 8388608, about 2x the final size copied in
    total.

## Debt and gaps

| id | what | status |
|---|---|---|
| D-DB19-1 | `aux` in `rpc.pruv` is still a fixed 8389120-byte buffer (detail at 0..300, raw error code from 512). Like the old `line`, it is untouched zero pages, so RSS is unaffected, but it still reserves 8 MiB of address space. Growing it needs the same `grow_line` pattern in `on_reply` and its contracts. | open |
| D-DB19-2 | `receive_grow` is a copy of `receive` with one changed branch. codex and mcp could move to it and `receive` could then be removed, but that changes their callers, which this lane does not touch. | open |
| G-DB19-1 | `Vec<u8>` is rejected at parse (`element_storage_type`: "u8 is only an array element type"), so the `inout line: Vec<u8>` of G-LG8-2 cannot be written. A `Vec<i64>` would cost 8x the bytes. The workaround is a `[u8]` that `grow_line` replaces with a doubled copy (`copy_range`). The language would need a growable byte vector (`Vec<u8>` or a `bytes` buffer with reserve/push) to grow in place. | open |
