# L3 DB49: mcp chain RSS (packet grows in place)

Lane: bench/l3/mcp/ (`packet.pruv`, `root.pruv`, `perf/perf_root.pruv`, `perf/perf_driver.rs`). No change in the compiler,
stdlib, SPEC, tests/, bench/l3/lib/ or bench/l3/pkgs/. The packet wire is unchanged (byte-identical, checked against hand below).
Baseline: main 4b58af26 (R04: 5x100 chain RSS 1.132x hand, D-R04-2; single cells +16/+32 KiB, D-R04-1).

## 1. Design (D-R04-2, G-R00-2)

Per-page RSS probe first (`perf_driver probe <row> <chain>`, resident bytes from `proc_pid_rusage` and the `ru_maxrss`
high-water mark after `load()` and after each page). 5x100 chain, resident bytes:

| Tree, row | after load() | after page 5 | page 5 minus load |
|---|---:|---:|---:|
| old (4b58af26), hand | 9175040 | 13221888 | +4.0 MB |
| old (4b58af26), new | 9175040 | 14958592 | +5.8 MB |
| DB49, hand | 9273344 | 13320192 | +4.0 MB |
| DB49, new | 9191424 | 9879552 | +0.7 MB |

`load()` (with its hand pre-pass for pages 1-4) costs the same ~9.2 MB for every row, so the harness is not the
difference and was not changed. The difference is the packet: `write` did `resize(p,want,0)` on a borrowed `p`, which copies
the whole previous packet into a new array while the old one is still live in the caller.

Change:

- `packet::write(take p: [i64], ...)` takes the caller's packet (R-6e-12). It binds `let mut q = move p;` and grows it with
  `q = resize(q,want,0)`. On an owned local the Rust backend lowers that to `Vec::resize` (checked in the generated `gen.rs`),
  so only the tail is zero-filled and the old packet is not live next to the new one. The final `truncate` shortens it in
  place. `lp = len(p)` is read before the move; the write range and the final length are unchanged, and the contracts are the same.
- `root.pruv` passes `move p` and reassigns `p` from the result on every path before the next use.
- `perf_root.pruv` `core_new` takes its packet the same way (`take p0`, `return move p0` when nothing is admitted).
  `keep_new` binds a copy before moving it (a direct `core_new(copy(p),...)` is rejected with `foreign_move`).
- `perf_driver.rs`: the new row owns its packet across the chain (`step()` hands `cur` over with `std::mem::take`); old and
  hand still borrow it. Page 0 needs an owned copy of `start`. `own()` makes that copy outside the timed call, the same way
  the borrowed rows get `start` for free. The `probe` mode is new; it is macOS-only and prints -1 when an RSS call fails.

LLVM still copies on `resize` (G-LG16-1), so this closes the copy on the Rust backend only (G-DB49-2).

At cells 0 and 1 the new row is faster than hand by construction: its owned input is made outside the timer, while hand
copies `start` into its output inside the call (D-DB49-1). On every other cell new time is within 1% of old and below hand.
On single cells new RSS is 16-64 KiB over hand (1.006-1.027x), and 16-80 KiB under old at the same time.
A 10-round run taken earlier at load 23-38, with the mutant run going alongside, gave the same RSS within one page and
5x100 at 0.577x time / 0.746x RSS.

RSS split (12-round quiet run; the gate run gives old 1760 / 1.964, new 1680 / 1.985, hand 1664 / 1.975): fixed = RSS at 0 tools; slope = (RSS at 500 - RSS at 0) / (out bytes at 500 - 5010*8).

| Row | fixed KiB | slope B per out byte | 5x100 minus fixed KiB |
|---|---:|---:|---:|
| old | 1696 | 1.980 | 12864 |
| new | 1712 | 1.975 | 7872 |
| hand | 1696 | 1.969 | 11152 |

The proportional part is now the same as hand on single pages. On the chain it is 0.71x hand (hand allocates a new output
each page). The fixed part is still +16 KiB (D-R04-1). Isolation: with a probe binary that runs two rows in one process at
0 tools, hand then new adds +16 KiB, new then hand adds 0, so the page belongs to whichever row runs first with its code. The new row
has no large stack frame (`run_new` reserves 0x110 bytes), but its inlined text is 21468 bytes against 2512 for `core_hand`.
The constant page is the code image of the generated row, which is compiler output and outside this lane (G-DB49-1).

## 4. Rows and gaps

| id | what | status |
|---|---|---|
| D-DB49-1 | Cells 0 and 1 time: the new row takes an owned input made outside the timer, and returns it moved when nothing is admitted; hand and old copy `start` into their output inside the call. So new/hand time at 0-1 tools (0.25x/0.57x) is a harness asymmetry, not a packet speedup. The same applies to `instr` (whole-process RSS): new's owned copy replaces the output hand allocates, so peak liveness is comparable (start + one packet in every row) | note |
| G-DB49-1 | Single-page RSS is still 16-64 KiB over hand (1.006-1.027x; +16 KiB already at 0 tools). Isolated to the new row's code image (`run_new` 21468 bytes of inlined text vs 2512 for `core_hand`), not data or stack. Shrinking it needs smaller generated code, which is in the compiler (outside this lane). The brief's target "every mcp gate cell RSS <= hand" is not met on single cells because of this | open |
| G-DB49-2 | LLVM backend: `resize` on an owned array still allocates and copies (G-LG16-1), so the chain RSS fix applies to the Rust backend only. Needs in-place resize in the LLVM lowering (compiler) | open |

Review notes not taken as must-fix: the review called the `instr` mode's `own()` copy a must-fix, because `/usr/bin/time`
measures the whole process. `instr` is used only for maximum RSS. The owned copy is the packet the new row then grows in
place, while hand allocates its own output from the borrowed `start`, so both rows hold `start` plus one packet. The probe
above and the per-page numbers agree. Recorded as D-DB49-1 instead. The two "should" notes (macOS-only `probe` symbols;
unchecked RSS calls) and the nit (`Vec::resize` may still move the prefix when it reallocates) were fixed.

Status: DB49: D-R04-2 closed: write takes the packet and grows it in place; 5x100 RSS 0.748x hand (was 1.133x), time 0.582x hand
Status: DB49: D-R00-2 closed: carried as D-R04-2, closed in DB49
Status: DB49: G-R00-2 partial: grow in place via take + owned resize on the Rust backend; LLVM still copies (G-LG16-1, G-DB49-2)
Status: DB49: D-R04-1 partial: single cells 1.006-1.027x hand (old 1.004-1.047x); constant +16 KiB isolated to the new row's code image (not data, not stack); fix is in the compiler (G-DB49-1)
