# L3 LG21: bounded shared rs check and one result per attempt, `?` operand checks without temporaries

Scope: G-LG20-1, the red `trace_infer` step of main CI run 44993420887 (6d767fae, LG20 merged) and G-LG20-3, which also
covers G-LG18-1. Both compilers (Python `pruvc/`, Rust `pruvc-rs/`) where the item has a Python side. No `bench/` file
is changed. G-LG20-2/4/5, G-LG18-2/3, G-LG15-1, G-LG16-1 and G-DB31-x are out of scope and unchanged.

Status: LG21: G-LG20-1 closed (the shared check of a query gets at most 2 s; a3 rs 26.5-26.8 s against 25.7-26.3 s for the LG19 binary, alternated three times (LG20: 39.1-39.4 s); per function, `turns::plan` went from 16.7 s shared + 16.2 s isolated to 2 s + 16.1 s; g10a_v_wait_equal stays `assert` in 0.02-0.03 s alone and 0.04 s next to two full `run_all.py` runs, the DB29 7-field struct repro verifies)
Status: LG21: CI trace_infer closed (the rs verifier retries in the isolated context only after a timeout or a cancel and reports that one result, so an unknown with another reason is the attempt's result as in verify.py; the remaining reason-text difference of two unknown inference attempts over byte-identical queries is `same_unknown` in tests/diff_trace.py, G-LG21-3)
Status: LG21: G-LG20-3 closed (the borrow split, inout root and effect checks on `?` operands run also when nothing is lifted before the `?`; `eat(read(s)?, move s)` is type/try_position in both compilers)
Status: LG21: G-LG18-1 closed (`Ok(use3(get(y)?, inout y))`, a `?` operand reading the root of an inout argument outside it with no temporaries, is type/try_position, the code SPEC section 6 gives for it, in both compilers)

## What landed

- Bounded shared check (G-LG20-1, rs only). Per-function timing of a3 (`LG21_STATS`, a stats build not committed)
  put 33 s of the 35.6 s solver time in `turns::plan`: its stage-0 queries end unknown on the 8 s timeout in the shared
  context and, after LG20, again in the isolated copy (16.7 s + 16.2 s). The count split staging added no time there.
  `Solver::check` in `pruv-proof/src/sys.rs` now gives the shared check `min(timeout, 2000)` ms (`SHARED_FIRST_MS`)
  and restores the full timeout after it; a query the shared context does not decide in 2 s goes to the isolated copy
  with the full timeout, as before. A query decided in the shared context in under 2 s (almost all) is unchanged; the
  DB29 perturbation (an unknown in the shared context) still gets the isolated copy.
- One result per attempt (CI `trace_infer`, rs only). The LG20 shared-first check retried every unknown in the
  isolated copy. An unknown with a reason other than a timeout (`incomplete quantifiers`, g10a_v_havoc_eof) then
  turned into `sat` in the copy, while `verify.py` checks once and records the unknown; `diff_trace --infer` reported
  this as a hard diff. `check` now retries only when the shared reason contains `timeout` or `canceled` (an exhausted
  rlimit) and otherwise returns the shared unknown with its reason; `model` and `reason_unknown` read the solver whose
  answer was returned, so the trace and the inference (which reads the same attempts) see one result per attempt.
- Reason text of two unknowns (CI `trace_infer`, `tests/diff_trace.py`). After the change above the two remaining
  diffs (g10a_v_havoc_eof seq 3, inf_budget seqs 54-56 and 59) are inference attempts that both answer `unknown` to a
  byte-identical query and differ only in Z3's reason text and the status derived from it (`canceled` / `timeout`
  in verify.py, `max. resource limit exceeded` / `resource_unknown` in the rs copy). The text depends on the history
  of the context, which the rs verifier does not reproduce, and the inference results are equal. `same_query_unknown`
  classifies that as `same_unknown`, next to `same_query_dropped`; any other field difference stays a diff.
- `?` operand checks without temporaries (G-LG20-3, G-LG18-1, both compilers). The split check (a `?` operand
  borrowing a name another argument of the same call moves or mutates), the inout root check and the effect check
  ran only from `try_temps`, which returns early when nothing is evaluated before the `?`. Python `try_checks` and
  the Rust equivalent now run them on every statement `find_try` lowers. Without temporaries, a builtin parent's
  argument counts as a read unless the builtin is `string_to_str`, the catalog parameter is `take`, or the argument is
  past the catalog parameters; a builtin outside the catalog (`len`) reads. An inout argument inside the `?` operand
  itself (`set(inout x)?`) does not count for the root check. SPEC.md section 6 (the `?` paragraph) states the rule.

## Gaps

| Id | Gap |
|---|---|
| G-LG21-1 | The 2 s cap of the shared check is a measured heuristic, not derived: a query that needs between 2 s and its timeout in the shared context now pays the copy into the isolated context. On a0-a4 and the test set no proof outcome changed, but a module whose queries mostly take over 2 s would pay the LG19 cost again. |
| G-LG21-2 | The retry filter reads Z3's reason text (`timeout`, `canceled`). A DB29-style perturbation that makes the shared context answer unknown with another reason (`incomplete quantifiers`) is not retried in isolation. None is known; the DB29 repro times out in the shared context and is retried. |
| G-LG21-3 | `tests/diff_trace.py` tolerates a different reason text and status of two unknown inference attempts over byte-identical queries (`same_query_unknown`). The rs verifier cannot reproduce the reason text of verify.py's context history; a real status bug confined to that field in inference attempts would be classed `same_unknown`. |
| G-LG21-4 | This lane used 6 release builds against a budget of 4: the CI `trace_infer` item added to step 1 needed builds 5 (retry dropped on every iso unknown, reverted) and 6 (the reason filter). |
