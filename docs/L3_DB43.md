# L3 DB43: grok/pkgs ord and dense time vs hand (D-DB15-1, D-DB15-2, D-DB42-1)

Base: main d9211558. Baseline: docs/L3_DB42.md (not re-surveyed). Lane: bench/l3/grok/, bench/l3/pkgs/{jstr,access,parse}/,
this doc. No compiler change.

## 1. Result in one paragraph

ord and dense still block, and no package source changes in this commit. Five in-lane rewrites of the string path
(parse `string_token`, jstr `string_utf8_scanned`, grok `framing::find_lf`) all pass `run_perf.py check` 5/5 but none
is faster than main at M or L, and two are slower, so they were all reverted (section 3). Experiments on the
generated Rust (section 4) show what the remaining gap is made of: the per-string UTF-8 check is about 15% of pruv
ord time, the adapter's extra copy is about 0%, and the rest is the tape + owned document design against a one-pass
hand parser. Closing that needs new design or a proof/compiler change (G-DB43-1, G-DB43-2). The quiet rerun of
D-DB42-1 is done at load 4.3-7.2.

## 3. Attempts (all reverted)

Each attempt: edit in the lane, `run_perf.py check` (verified build, 5/5 `pruv == hand`), then old/new/hand alternate.

| # | change | ord M/L new vs old | dense M/L new vs old |
|---|---|---|---|
| 1 | `string_token` block test re-entered after each escape, jstr 16-byte block search for `\`, `find_lf` 16-byte block | 1.82x vs 1.94x at M (-6%) | 1.51x vs 1.44x (+5%) |
| 2 | `string_token` and jstr as plain byte loops | slower than old | - |
| 3 | `string_token` one combined block loop | slower than old | - |
| 4 | hand-like `string_token` (byte loop, one `utf8_valid` per non-ASCII string, exact fallback) + one-pass jstr decoder writing into one buffer with `truncate` | 1.97x vs 1.97x (0%) | 1.51x vs 1.45x (+4%) |
| 5 | whole-line `utf8_valid` once in `scan_into` (lines >= 64 bytes) and a `trusted` flag that skips the per-character UTF-8 work in `string_token` (old block form, or the byte form of #4) | +2% to +15% slower | +2% to +4% slower |

`find_lf` as a 16-byte block was slower than the byte loop on its own. 16-byte tests written as i64 min/max over
`|b - x|` are widened by LLVM to i64 lanes and lose to the byte loop; the lane has no byte-lane SIMD form.
Attempt 1 is the only ord gain and it costs dense, so it does not meet "no cell worse".

## 4. What the remaining ord gap is made of

Experiments edit the generated `gen.rs` of attempt 4 by hand (scratch only, not a Pruv change), 3 rounds at load 5:

| variant | ord-2m pruv ns | vs attempt 4 |
|---|---:|---:|
| attempt 4 as compiled | 6726541-6787958 | - |
| B: jstr bytes moved into `String::from_utf8(bytes)` instead of the adapter's `from_utf8 + to_owned` copy | 6731666-7108354 | 0% |
| C: per-string UTF-8 check in `string_token` stubbed to `true` | 5733209-5935062 | -15% |
| B + C | 5652375-5679750 | -16% (10 rounds: ord M 1.62x, L 1.63x) |

- The second copy of every decoded string (adapter `to_owned`) costs nothing measurable; `string_to_str` already
  moves at its last use.
- A content string is UTF-8-checked twice (in `parse::string_token`, then in the `str` adapter `utf8_to_string`)
  where hand checks each line once. Dropping one check is worth about 15%, but only a proof can drop it: either the
  token's validity flows to the decoder output and the adapter becomes an unchecked conversion, or the line check
  flows into `string_token` (attempt 5 did the line check at run time and lost more than it saved). Both need an
  encoding/compiler change (G-DB43-1).
- With both removed pruv is still 1.62x. A profile of B + C (ord-8m, every function `inline(never)`) shows the rest
  spread over the second pass of every string (`string_token` to find the end, then jstr to decode, then the adapter
  check; hand decodes once while scanning), `find_lf`, the tape, `lines::build_span` (owned copy of the line and tape
  per user/assistant line, outside the lane), and field lookups in `entry::feed`. Hand (`hand_history.rs`
  `history_window`) parses each line once straight into the entry. That is a different reader design (G-DB43-2).

Dense: the profile is `parse::scan_into` first (505 of about 1500 samples), then `line_step`, `view_root_type`,
`skip_whitespace`, `find_lf`. `read::line_step` builds `json::parse_failed(0, 18)` before its branch, but it is a
plain enum and LLVM drops it (checked in `gen.rs`), so there is no cheap per-line fix there.

## 7. Step 3: run_perf.py pairs

`run_perf.py` takes `--pair py/rust|py/llvm|rs/rust|rs/llvm` (default `rs/rust`, same command and `work/` paths as
before). `py/*` runs the checkout's `pruvc/pruvc.py`; `*/llvm` emits `gen.ll` with `--rust-bindings gen.rs` and links
the LLVM object and runtime through `bench/g2/run.py` `build_llvm_objects`. Non-default pairs build in
`work/<pair>/`; rows are shared. Checked here: default rs/rust and py/rust on hist-ord-64k and hist-dense-2m, rs/llvm
on hist-ord-64k, all `pruv == hand`; the writer also checked py/llvm on hist-ord-64k. Times for the other pairs were
not measured (load 14-26 after 02:29, see G-DB43-3).
