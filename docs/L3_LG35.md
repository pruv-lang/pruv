# L3 LG35: consuming match-arm binder moves on LLVM, one UTF-8 check under --no-verify, ABI shrink kept

Scope: G-LG34-1 (the array binder of a consuming `match` arm still copies under `truncate` / `str_from_utf8` on
LLVM), G-DB57-2 (the 945,570-byte realloc in the codex ABI wrapper), G-DB56-3 (the second UTF-8 check under
`--no-verify`). Base: main c9dde1e0. No bench source and no older L3 doc was edited.

Status: LG35: G-LG34-1 closed (LLVM moves the consuming match-arm array binder into `truncate` / `str_from_utf8` at its last use, both compilers; tests on both backends)
Status: LG35: G-DB57-2 closed (the shrink stays, D-LG35-1; traced: the 1,048,576 -> 945,570 realloc stays in place in every run)
Status: LG35: G-DB56-3 closed (under `--no-verify` a `str_from_utf8(x)` right after an `&&`-guard `utf8_valid(x)` is not checked again, both backends and compilers, D-LG35-2)

## Step 1: consuming match-arm binder move on LLVM (G-LG34-1)

D-LG35-3 (closes D-LG34-2 / G-LG34-1): on LLVM a match payload binder is an SSA view of the owner enum's payload field
(`V.mv = (owner slot, ctor, field, own_dead)`), not a slot. `move_src` of `truncate(t, m)` / `str_from_utf8(t)` now
accepts such a binder when the owner is dead after the match (`own_dead`, the same test that makes the Rust backend
emit `match p` by value) and the binder is dead after the statement or the next statement of its block is a `return`
that does not name it (the Rust backend's `last_copy`). The lowering takes the block through `take_array`: for a slot
it empties the slot as before, for a binder it stores `{ptr, i64, i64} zeroinitializer` into the owner's payload field,
so the enum cleanup frees null and no other path can reach the block. The moved `truncate` then follows the slot path
(D-LG33-1: `pruv_shrink_v2` to `m` only when more than half of the cap is unused). A binder read later, an owner read
after the match, a binder named in the `truncate` length, a binder assigned to its own name, or an owner that an
enclosing match arm still borrows (both LLVM generators now pin the scrutinee root while the arms are lowered, like
the Rust backend's `pinned`; found by the review) keeps the copy.
Both compilers emit the same IR.

Tests: `tests/runtime/lg35_rt_binder_move` (default and `--no-verify`, both backends, allocation balance): `cut`
(`truncate` of the binder, then return), `word` (`str_from_utf8` of the binder), `keep_binder` (binder read after the
call: copy), `keep_owner` (owner read after the match: copy), `nested` (an inner match on the owner of a still-open outer arm:
copy, the write is not seen through the outer binder).

## Step 2: ABI wrapper shrink (G-DB57-2)

The ABI wrapper of an exported function that returns an array or string calls `pruv_shrink_v2` when `cap != len`
(`pruvc-rs/crates/pruv-core/src/abi.rs` wrapper, `pruvc/llvmgen.py` ABI wrapper) because the host side rebuilds the
buffer with `Vec::from_raw_parts(data, len, len)` and frees it with exactly that layout (`bindings.rs` host glue).

Trace (scratch DYLD malloc interposer, one read per process, measure_r09 scenarios, 3 runs each, stdout matched hand
every run; new build, py/llvm runner; py and rs emit byte-identical IR):

| cell | shrinking realloc | moved | bytes | blocks | live peak |
| --- | --- | --- | --- | --- | --- |
| L | 1,048,576 -> 945,570 | 0 of 3 | 9,547,780-9,596,146 | 3,913-3,919 | 1,432,416-1,436,720 |
| M | 262,144 -> 236,468 | 0 of 3 | 2,667,650-2,765,777 | 1,173-1,183 | 729,264-762,032 |
| hand L / M | none | - | 6,168,387 / 1,638,609 | 13,396 / 3,380 | 1,188,272 / 470,752 |

The shrink never moved the block: macOS malloc shrinks a large block in place, so it costs no copy and returns the
tail pages. The codex emission is byte-identical before and after this change on every pair (`root_gen.rs` /
`root_gen.ll` diff 0 lines), so the allocated bytes before and after are the same; they match DB57's rs/llvm L row
(9,546,927 old, 9,547,195 new).

D-LG35-1: the shrink stays. Dropping it would hand the host a block whose capacity differs from the length it
rebuilds the `Vec` with, which breaks the `from_raw_parts` / dealloc layout contract; keeping the spare capacity needs
a cap field in the ABI structs on both compilers' wrappers and bindings, an ABI change, for a realloc that the trace
shows is in place.

## Step 3: one UTF-8 check under --no-verify (G-DB56-3)

D-LG35-2: `codegen.utf8_checked(if)` (Python) / `codegen::utf8_checked` (Rust) returns the `str_from_utf8(x)` call
that is the whole value of the first statement (`let`, non-deref assignment or `return`) of an `if` whose condition is
an `&&` chain with a conjunct `utf8_valid(x)` on the same variable and no `inout` argument anywhere in the condition.
When every conjunct is true the bytes of `x` were just checked and nothing ran in between that could change them, so
both backends lower that one call unchecked under `--no-verify` (Rust: `from_utf8_unchecked`; LLVM: no
`@pruv_utf8_valid` call and no panic path). The rule is syntactic and narrow on purpose: a guard under `||` or `!`, a
statement between the check and the decode, or a decode deeper in the block keeps the check. With verification on,
nothing changes (the proof already removes the check).

Tests: `tests/runtime/lg35_rt_utf8_once` (`--no-verify`, both backends): `once` and `keep` lose `@pruv_panic_utf8`,
`either` (`||`) and `later` (a statement in between) keep it; the Rust backend emits the unchecked form for both the
moving and the borrowing decode.
