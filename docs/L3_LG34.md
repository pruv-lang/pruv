# L3 LG34: one last-use move condition on both backends, field-target regrow, narrow regrow

Scope: G-LG33-3 (stale `pruv_shrink_v2` comment), G-LG33-2 (the `truncate` / `str_from_utf8` move condition differs
by backend), G-LG32-3 / G-LG33-4 (`x.f = resize(x.f, n, v)` regrow, and regrow of every scalar element kind). No
bench source and no older L3 doc was edited.

Status: LG34: G-LG33-3 closed (the `pruv_shrink_v2` comment names its real callers)
Status: LG34: G-LG33-2 closed (one move condition, `dead_after or return_next`, on both backends and both compilers; the consuming match-arm binder copy is kept as D-LG34-2 / G-LG34-1)
Status: LG34: G-LG33-4 closed (LLVM regrow covers `[u8]`, `[bool]`, `[i64]` and the u8 / u16 / u32 narrow layouts)
Status: LG34: G-LG32-3 closed (`x.f = resize(x.f, n, v)` with the same field path regrows in place on both backends)

## Step 1: `pruv_shrink_v2` comment (G-LG33-3)

The header comment of `pruv_shrink_v2` in `pruvc/runtime.c` now names its callers: the LLVM `truncate` move
(D-LG33-1, `nc = m` when more than half of the cap is unused, else `nc = cap`) and the ABI wrappers that hand a
block over with `len == cap`. No other copy of the comment exists (pruvc-rs reads `runtime.c` in place).

## Step 2: one move condition (G-LG33-2)

D-LG34-1: the LLVM `move_src` of `truncate(x, m)` / `str_from_utf8(x)` in a `let` or assignment now accepts
`dead_after(x) or return_next(x)`, the same two conditions as the Rust backend's `last_copy`. `return_next` is new on
LLVM: each block frame records whether the next statement of the block is a `return`; when it is and that `return`
does not name `x`, `x` is dead after the statement even inside a loop body (control leaves the function first). An
owned (take) parameter is never moved by this rule (the Rust backend's `return_next` rejects every parameter; on
LLVM a borrowed parameter is not an owned slot, so the two sets agree). Both compilers emit the same IR.

D-LG34-2: the remaining LLVM-only copy. The Rust backend moves any local in `vt`; LLVM moves only an owned array
slot. The array binder of an arm of a `match` that consumes an owned enum is in `vt` on the Rust backend, so
`truncate(t, m)` / `str_from_utf8(t)` at its last use moves the payload `Vec` there; on LLVM the binder is an SSA view
of the payload field (not a slot), so the call allocates and copies, and the enum's cleanup frees the payload. Moving it
would need the binder to own the payload block and the enum cleanup to skip it. Kept; a P3 stack-placed array never
reaches this case (a `truncate` / `str_from_utf8` use removes the local from the stack candidates).

`copy(x)` was already on the same rule (`dead_after` only) on both backends and is unchanged.

Test: `tests/runtime/lg34_rt_move_return` (`cut`: `truncate(t, 1)` then `return` inside a loop, `t` read after the
loop; `word`: `str_from_utf8(b)` then `return` inside a loop; `keep`: the `return` reads `t`, so it copies), with
`llvm_fn_absent` of the copy helpers on `cut` / `word`, `llvm_fn_contains @pruv_copy(` on `keep`, and the Rust
backend's move text in `gen_contains`.

## Step 3: field-target regrow and narrow regrow (G-LG32-3, G-LG33-4)

D-LG34-3: `x.f = resize(x.f, n, v)` (and deeper paths `x.a.b = resize(x.a.b, n, v)`) with the same field path on
both sides, on an extended struct local or `inout` struct parameter, lowers to the in-place regrow on both
backends: Rust `x.f.resize(n as usize, v)` (with the `--no-verify` guards of `resize_expr`), LLVM the regrow helper
of the field's element kind on the field's block, storing back the block, `n` and cap `max(n, cap)`. Soundness: the
statement overwrites the very field it reads, so the old value has no other reader after it; the generic path
already freed the old block at this store, so any alias that a realloc could invalidate was already invalidated
(and Pruv has no aliasing borrow of a field across a statement). A different source field (`e.w = resize(d.w, ...)`),
or a field of a non-struct is left to the generic path (fresh block plus copy). A `Box` in the middle of the path
(`a.b.w` with `a.b: Box<..>`) is dereferenced like any field read; the choice depends only on the last field being an
unboxed scalar array field of a struct, so `a.b.w = resize(a.b.w, n, v)` regrows too.

D-LG34-4: LLVM regrow now covers every scalar element kind: `[u8]`, `[bool]` (zero-extended fill), `[i64]` and the
narrow storage layouts (`[i64 | lo..=hi]` stored as u8 / u16 / u32 under the verifier) through the new
`@pruv_regrow_narrow(s, cap, m, n, v, size, align)` (grow by `pruv_regrow_v2` when `n > cap`, then a memset for a
zero or byte fill, else a 16- or 32-bit store loop). Before, a narrow-layout `x = resize(x, n, v)` fell back to
`pruv_resize_narrow` (fresh block plus copy).

Tests: `tests/runtime/lg34_rt_field_regrow` (inout struct parameter, nested struct local, `[i64]`, `[u8]`, `[bool]`,
and a different-source field that must stay generic) and `tests/runtime/lg34_rt_regrow_narrow` (u8, u16 and u32
storage; each grows past the cap, truncates by one and grows back inside the cap, then grows past the cap again,
and the u32 case also regrows to the same length with a nonzero fill; every filled element is printed; `llvm_fn_contains`
`@pruv_regrow` and `llvm_fn_absent` of `@pruv_resize_narrow(` / `@pruv_resize(`). The existing
`tests/runtime/lg3_rt_inout_struct` (`s.w = resize(s.w, len(s.w) + 4, 9)` on an inout parameter) now takes the regrow
too.

## Emitted output, old against new

Old is main `f7dd7978` built as `836e2eca`, new is this change. Both compilers were run on every bench root and on every runtime test.

- Rust backend: 38 bench outputs compared, 0 failed, every Rust-backend output identical.
- LLVM: 13 outputs differ (codex, grok, opencode, mcp, qwen, claude a0 / a1 / a2 / a4, json a2 / a3 / a4 / a5), all with the same single change in the shared json `scan_document`. One `pruv_copy` of a `truncate` followed by a `return` becomes the move: the slot is emptied, the `pruv_shrink_v2` cap test runs, and the values are renumbered (D-LG34-1).
- Runtime tests (Python compiler, 902 outputs): only `lg3_rt_inout_struct` differs, with the intended field regrow (D-LG34-3).

## Performance

grok `hist-ord` / `hist-dense`, M and L, on rs/rust and rs/llvm. Old and new alternate for 10 rounds at 400 ms per sample, with load 9.1 to 11.0. Every sample's output matched hand (`pruv == hand` on every check). The M / L cells are the proportional part under `tools/perf_gate.py`. Cell files are `work/lg34_grok_<pair>/perf_cells_<pair>_{new,old}.json` (not committed).

| Id | Difference | Why | Kept |
|---|---|---|---|
| D-LG34-1 | on LLVM, `truncate(x, m)` / `str_from_utf8(x)` in a `let` / assignment also moves an owned local array `x` when the next statement of the block is a `return` that does not name `x` (`return_next`), as the Rust backend already did | one move condition on both backends (G-LG33-2) | kept |

| D-LG34-3 | `x.f = resize(x.f, n, v)` with the same field path, on an extended struct local or inout struct parameter, regrows the field's block in place on both backends | the generic path kept the old and the new block live together (G-LG32-3) | kept |
