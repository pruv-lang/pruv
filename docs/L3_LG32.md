# L3 LG32: LLVM `window` codegen (UTF-8 block scan) and in-place regrow for `x = resize(x, n, v)`

Scope: G-DB53-3 (grok ord M/L time above hand on both LLVM pairs), G-DB52-4 (codex L RSS on the LLVM pairs about
1.4 MB over the Rust pairs) and, if time was left, G-DB53-1 (text size per function). G-DB51-1, G-DB50-1, G-DB52-1/2
and G-LG31-1..6 are out of scope and unchanged. No bench source (bench/l3/lib, codex, pkgs) was edited.

Status: LG32: G-DB53-3 closed (UTF-8 validation scans 16-byte aligned ASCII blocks, both compilers through the shared `pruvc/utf8_valid.ll`; grok ord rs/llvm M / L 1.016x -> 0.994x / 0.867x -> 0.849x hand in one alternating 10-round run at load 6-20; the remaining stop-loop shape is G-LG32-1)
Status: LG32: G-DB52-4 partial (`x = resize(x, n, v)` on a local or parameter array now lowers to one realloc on the LLVM backend instead of a fresh block plus copy with both blocks live, both compilers; the codex 1.4 MB is not this path: an alloc trace puts about 0.93 MB of it on `wire = truncate(hb, m)` (read.pruv:254), lowered as a fresh block plus copy while `hb` is live; G-LG32-5, G-LG32-2, G-LG32-3)
Status: LG32: G-DB53-1 open (not started in this lane, time; G-LG32-4)

## Step 1: `window` on the LLVM backend (G-DB53-3)

An instruction-level profile of `read::window` (grok perf driver, hist-ord-2m/8m, rs/llvm against rs/rust, a
pc-sampling interposer) put the extra LLVM time in `pruv_utf8_valid`: the Rust backend calls `std::str::from_utf8`,
which skips aligned ASCII words, while the LLVM backend's hand-written IR checked one byte per iteration. The
ordinary rows are mostly ASCII JSON, so that loop was the gap.

D-LG32-1: `pruvc/utf8_valid.ll` (included by both compilers) now, at a 16-byte aligned ASCII byte, reads two aligned
`i64` words per step and skips the block when no byte has its high bit set; on the first block with a high bit (or
fewer than 16 bytes left) it resumes the byte loop at that block, never before the byte already known to be ASCII.
The function still accepts exactly the UTF-8 the byte loop accepts (the block path only skips bytes `< 0x80`, which
the byte loop accepts one by one). Instructions retired by `window` on hist-ord-2m fell about 5%.

Tried and not kept: `!noundef` on the byte loads (1.4% slower). The remaining difference to `from_utf8` is the
per-byte stop loop and the order of the multibyte switch (G-LG32-1).

## Step 2: in-place regrow (G-DB52-4)

The LLVM backend lowered `x = resize(x, n, v)` as any `Assign`: evaluate `resize` (a fresh block of `n` elements
plus a copy of the old ones), then free the old block, then store. The old and new blocks were live together and
there was no `realloc`. D-LG32-2: when the assigned value is a call `resize(x, n, v)` whose first argument is the
same plain name as the target, the slot is an array, and the element is `u8`, `bool` or an `i64` layout, both
compilers emit `@pruv_regrow_u8` / `@pruv_regrow` instead: the same guards as `resize` (negative length, length
limit), then `pruv_regrow_v2` (runtime.c) only when `n` exceeds the capacity, a fill of `[old len, n)` with `v`
(memset for bytes and for zero, a store loop otherwise), and the slot keeps the block with capacity
`max(n, cap)`; the old block is not freed separately. `pruv_regrow_v2` uses the host Rust allocator's realloc
under `PRUV_RUST_ALLOCATOR` and libc `realloc` otherwise, so the alloc-count balance (`PRUV_COUNT_ALLOCS`) is
unchanged (smoke: `4 4`). The Python and Rust compilers emit byte-identical IR for the smoke program in both modes.

Sites in the benches that take the new path: claude `turns.pruv:125`, codex `read.pruv:183` (`hb`), grok
`line.pruv:563` and `read.pruv:349`, mcp `packet.pruv:344`, qwen `import.pruv:315`.

The codex L RSS gap is not explained by this: codex's big grows go through `grow_bytes` (read.pruv:63,
rpc.pruv:125) which takes the buffer by value and returns `resize(buf, ...)`, so it is a call result, not a
same-name assign, and keeps the fresh-block form. D-DB52-1 (the in-place `inout` `grow_bytes`) would turn those into
same-name assigns that now regrow; it is a codex source change, outside this lane (G-LG32-2).

Trace of the codex L gap (a malloc interposer that logs every alloc/realloc/free with its caller, the r09 runners of
py/llvm and rs/rust, the L payload): peak live heap 2,397,040 bytes on py/llvm against 1,972,288 on rs/rust. At the
LLVM peak two blocks are live: the 1 MiB `hb` read buffer and a fresh 945,570-byte block allocated by
`pruv_host_alloc_v2` from `codex_read_wire` (symbolized with `atos`); the 1 MiB block is freed right after the copy.
The Rust pair holds 1 MiB + 512 KiB at its peak and reuses `hb` as the output. The source line is
`wire = truncate(hb, mv + col.text_len);` (read.pruv:254): outside `return truncate(x, m)` (P3), both compilers
lower `truncate` to `pruv_copy_v2`, a fresh exact-size block plus copy, while `hb` is still live. That accounts for
about 0.93 MB of the 1.4 MB. Lowering a truncate whose source dies at the assign as a move (same block, length `m`)
or a shrinking realloc is a compiler change; no build was left in this lane (G-LG32-5).

RSS: see "Measurements".

## Measurements

grok ord, `window` only (the perf driver of `bench/l3/grok/perf`, built by `run_perf.py check` with the old pruvc
binary and with this one; 10 alternating rounds, order rotated, median of per-process medians of 400 ms; load 6.3
at start, 19.6 at end, other lanes running):

| row | old rs/llvm | new rs/llvm | rs/rust | hand | old / new (x hand) |
|---|---|---|---|---|---|
| hist-ord-2m (M) | 5.084 ms | 4.974 ms | 4.777 ms | 5.004 ms | 1.016x / 0.994x |
| hist-ord-8m (L) | 22.43 ms | 21.97 ms | 19.18 ms | 25.87 ms | 0.867x / 0.849x |

The L hand median rose with the load spike, so the L x-hand values are low for every side; old against new is the
reading that matters (-2.2% M, -2.0% L). py/llvm emits the same IR as rs/llvm (diff_rust all same, smoke IR equal);
it was not timed separately. The Rust pairs do not use either changed file.

codex r09 (`measure_r09.py --rounds 5`, this compiler, peak RSS by `time -l`, other lanes running):

| pair | M time (x hand) | L time (x hand) | M RSS (x hand) | L RSS (x hand) |
|---|---|---|---|---|
| py/rust | 161.7 ms (1.029x) | 438.8 ms (1.007x) | 4.54 MB (1.583x) | 6.03 MB (1.665x) |
| py/llvm | 165.2 ms (0.988x) | 445.9 ms (1.035x) | 4.60 MB (1.561x) | 7.36 MB (2.041x) |
| rs/rust | 169.5 ms (0.987x) | 359.1 ms (0.771x) | 4.54 MB (1.565x) | 6.54 MB (1.814x) |
| rs/llvm | 175.5 ms (1.009x) | 369.8 ms (0.828x) | 4.69 MB (1.580x) | 7.27 MB (2.009x) |

The LLVM L RSS is still 0.7 to 1.3 MB over the Rust pairs, as expected: the regrow does not touch codex's big
buffers (above), and the traced 0.93 MB is the `truncate` copy (G-LG32-5). Time moved with the load (the py and rs
L rows differ by 20% on the same code); no time claim is made from this run.
