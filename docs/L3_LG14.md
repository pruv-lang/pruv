# L3 LG14: temporaries for operands evaluated before a `?`, and the three LG13 diagnostic gaps

Scope: wave 1 of `docs/LANG_ROADMAP.md` (typed errors and `?`). Both compilers (Python `pruvc/`, Rust `pruvc-rs/`)
change with the same output. No `bench/` fragment is changed.

Status: LG14: G-LG13-1 partial (a call, constructor, move, index, arithmetic, unary `-` or string literal before a `?` is bound to a fresh temporary; a statement with inout, or an earlier operand with a quantifier, a subview, a move of a name used again, a name moved elsewhere or a non-value type stays rejected, G-LG14-1..2)
Status: LG14: G-LG13-5 closed (a `?` in a pred fn return is `type/try_position` in both compilers, checked before `type/pred_signature`)

## What landed

- Temporaries before a `?` (G-LG13-1 partial). `find_try` now keeps the path from the statement's root to its first
  `?`. On every node of that path, each child evaluated before the path child that is not wholly pure (pure: a
  local, a non-string literal, a field access, `!`, a comparison or a logical operator) is bound first:
  `let __pruv_try_tN: T = <operand>;` is inserted before the statement, left to right, the operand is replaced by
  the local, and the statement is processed again (so the next `?` of the same statement, which may have the first
  `?`'s result before it, gets its own temporary). `return Ok(g(x) + f(x)?);` becomes
  `let __pruv_try_t0: i64 = g(x); match f(x) { Ok(__pruv_try_v1) => return Ok(__pruv_try_t0 + __pruv_try_v1), .. }`.
  The earlier operand still runs, and its preconditions and index bounds are still proved, before the `?`; a
  short-circuit operand is bound whole, so `(false && b()) == x?` keeps its skipping. Temporaries and the `?`
  names share one counter (Python `try_index`, Rust `try_count`), so both compilers emit the same names. Python
  `find_try` / `try_temps`, Rust `find_try` / `try_temps` / `try_site_mut`.
- A `?` stays `type/try_position` when a temporary would change the meaning: the statement passes any `inout`
  argument (the inout call's alias, effect-order and outside-read checks would no longer see the earlier operand),
  the earlier operand contains a quantifier or a `subview`, it moves a name that the statement mentions again or
  mentions a name the statement moves elsewhere (a borrow bound early hides its conflict with the move), or its type
  is `()` or not a value type (a `String`, collection, reference or a type
  holding one, whose temporary would be dropped or borrowed at another point). The message names the pre-audit cases only (G-LG14-3).
- G-LG13-7: a quantifier before a `?` marks the operands as impure in both compilers, so it is `type/try_position`
  instead of `contract_only`.
- G-LG13-6: an assignment `x = ..` that passes `x` (or a field of it) `inout` in a statement with a `?` is
  `type/inout_context` ("x is passed inout and also mentioned elsewhere in this statement") in both compilers. The
  check runs before the `?` is located, so it also holds when the statement reads another local.
- G-LG13-5: a `?` in a `return` of a `pred fn` is `type/try_position` in both compilers; the check runs before the
  `type/pred_signature` check (`x_prepare` and the pred branch of the fn check, in both compilers).
- SPEC.md: the `?` paragraph (section 6c) and the `type/try_position` error row.

## Tests

- `tests/runtime/lg14_try_temps` (both backends, three flag sets, `g6_drop_balance`): a call before a `?`, an index
  and arithmetic before a `?` in a let, two `?` with calls and arithmetic before each, and a `move` before a `?`
  with a `String` error.
- must_reject: `lg14_try_temp_string` (a `String` operand before `?`), `lg14_try_after_quant` (G-LG13-7),
  `lg14_try_inout_assign` (G-LG13-6, `inout_context`), `lg14_try_pred` (G-LG13-5), `lg14_try_move_reused`, and the
  seven audit cases `lg14_try_temp_inout_read`, `lg14_try_temp_io_inout`, `lg14_try_temp_borrow_move`,
  `lg14_try_temp_nested_inout`, `lg14_try_pred_ctor`, `lg14_try_inout_assign_read` (`inout_context`),
  `lg14_try_temp_subview`.
  `lg13_try_after_call` and `lg13_try_after_index` are now valid in their old form and were changed to an inout call
  before the `?` and an index whose position passes `inout`.

## Gaps

| Id | Gap |
|---|---|
| G-LG14-1 | An operand of a non-value type (`String`, collection, reference) evaluated before a `?` is still `type/try_position`; binding it would need the temporary's drop and borrow points to match the unlowered expression. |
| G-LG14-2 | An earlier operand in a statement that passes `inout`, or one that contains a quantifier or `subview`, moves a name used again or mentions a name moved elsewhere, is still `type/try_position` (conservative: the unlowered program might be valid, or rejected with `inout_alias` / `inout_context` / `foreign_borrow` / `view_context`). |
| G-LG14-3 | The `type/try_position` message lists "one with inout, a quantifier, a move of a name used again or a type that is not a value"; it does not name the statement-level inout, `subview` and moved-elsewhere cases added after the audit (same text in both compilers; SPEC.md has the full list). |

## Audit

One review (Codex gpt-6.2-astra, ultra) found seven must-fix issues, all fixed in both compilers: (1) a read of `x`
bound to a temporary hid `inout_alias` with a later `inout x` in the same call; (2) an `io` call bound to a temporary
hid the `inout_context` effect-order check; (3) a borrow `len(s)` bound to a temporary hid `foreign_borrow` with a
later `move s`; (4) a nested `?` let the outer inout `?` read another binding, because temporary reads were not
counted; (5) a pred return with a constructor operand gave `pred_signature` in Python and `try_position` in Rust;
(6) `x = set(inout x)? + y` skipped the G-LG13-6 check because the `?` was not lowerable; (7) a `subview` direct
argument bound to a temporary gave `view_context`. Fixes: no temporaries in a statement that passes `inout`
(1, 2, 4; temporary reads are counted again), no temporary that mentions a name moved elsewhere (3) or contains a
`subview` (7), the pred `?` check also in Python `x_prepare` (5), and the G-LG13-6 check before the `?` is located
(6). One recheck (same model) found all seven fixed, with the same code and line in both compilers.
