# L3 DB54: Codex line parse without the range copy (G-DB52-1, G-DB52-2)

Brief: (1) G-DB52-1, `lines::parse_range` copies the line (25,347 bytes live at the L peak): parse a range of the
caller's buffer without a copy and switch codex to it. (2) G-DB52-2, `jstr::string_utf8` then
`pruv_str::utf8_to_string` build the same text twice, and `parse::widened` copies the tape on growth. Runtime copies
and compiler changes are out of scope. Base: main 69baedd2. One release `pruvc-rs` build from this base; no compiler
change.

## Where the code is

The brief names `bench/l3/lib`, but no L3 piece compiles `bench/l3/lib`: every piece (json, mcp, qwen, supervisor,
codex, ...) builds with `--manifest pruv.json` against `bench/l3/pkgs/*`. `parse_range`, `jstr`, and `parse::widened`
that codex runs are the `pkgs` copies, which are outside this lane. So item 1 is done inside codex, and item 2 is
recorded (G-DB54-2, G-DB54-3). `bench/l3/lib` is unchanged.

## What landed

- `bench/l3/codex/rpc.pruv`: new private `parse_owned(take data, hi)`, the body of `pkgs/lines` `parse_range(data,
  0, hi)` after its copy loop: the same limit check, `validate_utf8(owned, 0, hi)`, `scan(subview(owned, 0, hi))`,
  `check_tape`, and the same `Failed` positions and kinds. On success the document's source is `truncate(owned, hi)`
  of the moved buffer; the Rust backend truncates in place (and `shrink_to_fit`s only if the capacity is over twice
  the length), the LLVM backend keeps the pointer (truncate of an owned local inside the returned literal). Same
  `doc_local` ensures as `parse_range`.
- `parse_line(inout line, n, st)`: if the trimmed line starts at 0 and no partial line is pending (`st[1] == 0`),
  it moves `line.data` into `parse_owned` and leaves an empty buffer that `receive` grows again for the next line;
  a line with leading whitespace still goes through `parse_range`. The four callers (`open` and the three loops in
  `root.pruv`) reset `ctl[6] = 0` after the call, which keeps `ctl[6] <= len(line.data)`.
- `pruv.json` / `root.pruv`: codex now names `parse` and `lex` directly (`mod parse; mod lex;`), since
  `parse_owned` calls `parse::scan` and `lex::validate_utf8`.

Audit (Codex gpt-6.2-astra ultra, Codex 2 account): no must-fix; `parse_owned` gives the same result as
`parse_range(data, 0, hi)` for every input, no line is lost, duplicated or read stale, and every call site resets
`ctl[6]`. Its one note: on Rust the `shrink_to_fit` may move the buffer (the `list` path starts with an 8 MiB line
buffer), so "no copy" means the explicit copy loop is gone.

## Decisions

| id | decision | why | status |
|---|---|---|---|
| D-DB54-1 | the no-copy parse is a codex-local `parse_owned`, not a `pkgs/lines` entry | pieces build against `bench/l3/pkgs`, which is outside this lane; `bench/l3/lib` is used by no piece | kept |
| D-DB54-2 | move the line buffer only when the line starts at 0 and no partial line is pending | the moved buffer must hold exactly the line from 0; a leading-whitespace line keeps `parse_range`, so results are the same for every input | kept |
| D-DB54-3 | the document's source is `truncate(owned, hi)` inside the returned literal | it is the form both backends shorten in place (Rust `Vec::truncate`, LLVM length only) | kept |

## Gaps

| id | gap | cause | owner |
|---|---|---|---|
| G-DB54-1 | json, mcp, qwen, supervisor and the other pieces still copy each line in `pkgs/lines` `parse_range` | the no-copy form lives in `bench/l3/codex/rpc.pruv` (`parse_owned`) because `bench/l3/pkgs` was outside this lane | pkgs lane: add `parse_owned(take data, hi)` to `pkgs/lines` and switch codex and the other line readers to it |
| G-DB54-2 | each non-plain JSON string is still built twice (`jstr::string_utf8` bytes, then `utf8_to_string`), 919,819 B / 403 blocks each at L | the code is `pkgs/jstr` (out of lane), and `str_from_utf8` always emits `String::from_utf8_unchecked(b.to_vec())`, so even a moved owned `[u8]` is copied again | compiler (a moving `str_from_utf8` for an owned local at last use) then pkgs/jstr (decode into the owned buffer and convert it) |
| G-DB54-3 | `parse::widened` still copies the tape on each doubling (614,400 B / 80 at L) | the scanner sizes the tape from 192 slots up; the copy is in `pkgs/parse` (out of lane), and LLVM `resize` copies (G-LG16-1) | pkgs lane (size the first tape from the input length, bounded by the proved tape cap) or compiler (in-place LLVM resize) |
| G-DB54-4 | codex allocated bytes flat (M +4.6% to -1.8%, L +0.6% to -0.8%) although the line copy is gone | after a move the empty line buffer is grown again for the next line; the runtime still copies each line into its queue and `ev_bytes` (G-DB52-1 runtime part) | runtime: hand the read bytes to the caller by move or read into the caller's buffer, then codex can drop `line` growth |

Status: DB54: G-DB52-1 partial (codex parses a line from position 0 in its own buffer without the `parse_range` copy; one M read peak RSS 0.9-2.8% lower on all four pairs, time not worse; the runtime queue copies and the `pkgs/lines` share remain, G-DB54-1, G-DB54-4)
Status: DB54: G-DB52-2 open (no change: the double decode needs a compiler change and `pkgs/jstr`, `widened` is in `pkgs/parse`; G-DB54-2, G-DB54-3)
