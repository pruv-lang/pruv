# L3 DB50: codex `hb` as one cap-sized zeroed buffer (G-DB48-2, G-DB40-1, G-DB44-2, G-DB46-3)

Brief: try the in-lane option of G-DB48-2: start the codex `hb` arena as one zeroed buffer at its proved cap
(8,700,000 bytes, `bench/l3/codex/root.pruv:124`) so that pages are touched only as written and `grow_bytes` never
runs; keep it only if every codex gate cell (M and L) RSS is at or under its current value and time is not worse;
measure the empty-read cost (G-DB44-2). Then, only if time is left, the part of G-DB46-3 inside `bench/l3/codex`.
Base: main c0a368d9. The rs compiler was built once from this base; no other compiler build.

## Result: rejected, nothing in `bench/l3/codex` changes

The change was one constant (`byte_buffer(65536)` -> `byte_buffer(8700000)`). It verified on rs/rust and its output
matched hand on M and L, but RSS on the 20-read gate batch rose from 4.47 to 12.89 MB (M) and from 5.73 to 13.48 MB
(L). The source was reverted; only this document is committed.

### Why: macOS `calloc` zeroes a reused large block

Both backends lower `alloc(n, 0)` to a zeroed allocation (`std::alloc::alloc_zeroed`, and
`pruv_raw_alloc_zeroed_v3` on LLVM), which is `calloc` on macOS. A fresh large `calloc` is backed by untouched
pages, but once the block is freed and a block of the same size is requested again (the next read in the same
process), libmalloc hands back the cached block and clears it with `bzero`, which touches every page. A C probe
(macOS 26.5, `calloc(n)`, write `w` bytes, `free`, repeated; peak `ru_maxrss`, baseline 1,376,256 bytes):

| n | w | 1 call | 20 calls |
|---|---|---|---|
| 8,700,000 | 0 | 1,409,024 | 10,125,312 |
| 8,700,000 | 1,000,000 | 2,408,448 | 10,125,312 |
| 1,048,576 | 1,000,000 | 2,392,064 | 2,408,448 |
| 2,097,152 | 1,000,000 | 2,392,064 | 3,440,640 |
| 4,194,304 to 134,217,728 | 0 or 1,000,000 | | n + 1.4 MB every time |

No size escapes it: from the second call on, the whole block is resident even when nothing is written. A
simulation of the current `hb` chain (calloc 64 KiB, `realloc` to double, zero the tail, write the text in 4.7 KB
steps, 20 times) gives 1,949,696 bytes for the M text (229,882 bytes) and 2,457,600 bytes for the L text (919,784
bytes); the cap-sized buffer gives 10,125,312 for both. `realloc` grew in place in every step of that simulation
(0 moves), so the doubling chain alone touches about its final capacity (1 MiB at L), not the "about 2 MiB" of
G-DB40-1. Even a perfectly sized `hb` would save at most the overshoot over the text (about 0.12 MB at L, about
30 KB at M).

The form that would not touch pages up front is an uninitialised buffer that is only appended to (`Vec<u8>` with
`reserve` + `extend_from_slice`). R-6e-18 / R-6e-19 allow that only for `Vec<i64>` and `Vec<bool>`; a byte vector
is a language and compiler change, outside this lane (G-DB50-1).

## Perf (old = main c0a368d9 rs/rust runner saved in /tmp/db50_base, verified; new = the cap-sized `hb`, verified)

10 alternating rounds, 20 reads per sample, 07:23 KST, load 10.7 -> 9.0. Preflight and every sample matched hand
stdout. Only the rs/rust pair was built for the trial (one verify of about 9 minutes per side): the change is one
constant and the effect is the allocator's, which is the same `calloc` on every pair. Cells:
`work/db50/perf_cells.json` (not committed).

| cell | time new / old / hand (ms) | time new / old (x hand) | RSS new / old / hand (MB) | RSS new / old (x hand) |
|---|---|---|---|---|
| rs/rust M | 55.31 / 55.08 / 40.38 | 1.370x / 1.364x | 12.89 / 4.47 / 2.85 | 4.523x / 1.569x |
| rs/rust L | 140.98 / 137.62 / 89.61 | 1.573x / 1.536x | 13.48 / 5.73 / 3.59 | 3.758x / 1.598x |

RSS split (fixed + proportional to text bytes, two-point fit from M and L): new 12.70 MB + 0.85x, old
4.05 MB + 1.83x, hand 2.61 MB + 1.07x. The cap-sized buffer moves 8.7 MB into the fixed term. Time is +0.4% (M)
and +2.4% (L).
