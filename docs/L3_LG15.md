# L3 LG15: `?` in the right operand of && / ||, and LLVM contracts on Result<_, String>

Scope: wave 1 of `docs/LANG_ROADMAP.md` (typed errors and `?`). Both compilers (Python `pruvc/`, Rust `pruvc-rs/`)
change with the same output. No `bench/` fragment is changed.

Status: LG15: G-LG13-2 closed (a `?` only in the right operand of && / || is lowered to a nested if in both compilers; a `?` inside a quantifier or in the right operand of the contract-only `==>` stays `type/try_position`; a statement with inout, or an operator holding a quantifier, a subview, a conflicting move or a non-value binding used again, stays rejected, G-LG15-1)
Status: LG15: G-LG12-4 closed (LLVM reads is_ok / ok_val / err_val of a Result<_, String> parameter in a runtime-checked requires, same result as the Rust backend; ok_val only for T = i64 or bool, G-LG15-2)
Status: LG15: G-LG12-5 closed (the same in a kept cost clause; the unsupported_type message names "kept cost clause" or "runtime requires")
Status: LG15: G-LG14-3 partial (the try_position message now names the statement-level inout, subview and moved-elsewhere cases and the new short-circuit cases, same text in both compilers; it is still one message for all cases)
Status: LG15: G-LG13-1 partial (unchanged: earlier operands are bound as in LG14; the short-circuit operator is a new lowering, not a temporary)
Status: LG15: G-LG14-1 open (not touched)

## What landed

- The language has no if-expression or ternary, so && / || (and the contract-only `==>`) are the only conditional
  operand paths.
- Short-circuit `?` (G-LG13-2). When the first `?` of a statement lies only in the right operand `R` of `L && R` or
  `L || R`, `find_try` returns that operator node. The statement is preceded by
  `let mut __pruv_try_tN: bool = D; if C { __pruv_try_tN = R; }` and the operator is replaced by the local, where
  `D, C` is `false, L` for `&&` and `true, !L` for `||`. The assignment is an allowed `?`
  position, so the `?` in `R` is lowered by the existing rules on the next pass, inside the `if`. The local shares
  the LG14 counter, so both compilers emit the same names. Earlier impure operands on the path to the operator are
  bound to temporaries first, as in LG14. Python `find_try.short` / `try_short`, Rust `find_try` / `try_short`.
- It stays `type/try_position` when the statement (after its earlier operands are bound and earlier `?` lowered)
  passes any `inout` argument, when the operator contains a quantifier or a `subview`, when it moves a name mentioned
  outside it or mentions a name moved outside it, or when it mentions a binding of a type that is not a value type
  and the statement, counted before its earlier operands are bound, mentions that binding again (the operator now runs before the rest of the statement, and a
  borrow and an implicit move would be split between the `if` condition and the `?`). A `?` inside a quantifier, or
  in the right operand of `==>` (contract-only, so not lowered), is always `type/try_position`.
- Equality with the hand-written program: `tests/runtime/lg15_try_short.pruv` and a copy whose `and_case` and
  `or_case` are written as the nested if by hand give the same Rust and LLVM output after renaming the locals
  (0 differing lines), and both verify; the proof sees the same lowered AST.
- LLVM `Result<_, String>` in contracts (G-LG12-4 / G-LG12-5). In a runtime-checked `requires` and a kept `cost`
  clause, `is_ok`, `ok_val` (`T` = `i64` or `bool`) and `err_val` of a parameter read the tag, the
  value and the `String` handle from the real `{ i1, L(T), ptr }` storage, so `len(err_val(r))` and similar work
  with the same result as the Rust backend. Other forms are `codegen/unsupported_type`; the message says "in a kept
  cost clause" or "in a runtime requires" (Rust: a separate diagnostic tag for the cost path).
- SPEC.md: the `?` paragraph and the Owned `String` errors paragraph of section 6c, and the `type/try_position`
  error row.

## Tests

- `tests/runtime/lg15_try_short` (both backends, three flag sets): `&&` in an `if` condition, `||` in a let, `||`
  in a `return Ok(..)`, an earlier call bound to a temporary before the operator, and an operator nested in the
  right operand of another.
- `tests/runtime/lg15_e2_contract` (both backends): `is_ok` / `ok_val` / `err_val` on `Result<_, String>` in a
  runtime-checked `requires` and a kept `cost` clause.
- must_reject: `lg15_try_short_quant` (a `?` inside a quantifier in the right operand), `lg15_try_short_quant_left`
  (a quantifier in the left operand of the operator), and the audit cases `lg15_try_short_imp` (`==>`),
  `lg15_try_short_borrow_move` (a borrow and a move of a `String` in the operator) and `lg15_try_short_implicit_move`
  (an implicit move in the operator before a read after it), and the recheck cases `lg15_try_short_temp_borrow` (a
  borrow in an earlier operand bound to a temporary and an implicit move in the operator, in one call) and
  `lg15_try_short_nonvalue` (a non-value binding used twice while a field of it is borrowed). `lg13_try_and_right` is valid in its old form and now passes
  `inout` in the statement.

## Gaps

| Id | Gap |
|---|---|
| G-LG15-1 | A `?` in the right operand of && / \|\| is still `type/try_position` when the statement passes `inout`, when the operator contains a quantifier or `subview`, when it moves a name used outside it or mentions one moved outside it, or when it mentions a non-value binding used again (conservative, like G-LG14-2); a `?` in the right operand of `==>` is always rejected. |
| G-LG15-2 | LLVM `ok_val` of a `Result<T, String>` in a runtime `requires` or kept `cost` clause supports only `T` = `i64` / `bool`, and only a parameter operand (a field path of a `Result<_, String>` cannot exist: `type/foreign_owned_type`); others are `codegen/unsupported_type`. |

## Audit

One review (Codex gpt-6.2-astra, ultra) found four must-fix issues and one should-fix: (1) `false ==> r?` in code was
lowered and so hid `type/contract_only`; (2) `id(len(s) > 0 && consume(move s)?)` lost `foreign_borrow`, the borrow
going to the `if` condition and the move to the `?`; (3) an implicit move `Err::<bool, String>(s)?` in the operator
was not counted; (4) `touch(inout x)? == (true && Ok::<bool>(true)?)` was accepted while SPEC said a statement with
`inout` is rejected; (5, should-fix) SPEC said "parameter or field path" for the LLVM `Result<_, String>` reads.
Fixes: `==>` is not lowered, a `?` in its right operand is `try_position` (1); an operator that mentions a non-value
binding the statement mentions again is `try_position` (2, 3); SPEC says the `inout` check is on the statement as left
after its earlier operands are bound and earlier `?` lowered (4, intended); SPEC says "parameter" (5). A borrow in an
operand before the operator and an implicit move inside it (`(len(s) > 0) == (true && Err::<bool, String>(s)?)`) was
first left accepted on purpose (the unlowered form is accepted). One recheck (same model) found 1, 2, 4 and 5 fixed and
two more cases: (a, must-fix) the same borrow and implicit move as arguments of one call, where the unlowered form is
`foreign_borrow`, was accepted because the earlier operand was bound to a temporary before the count; (b, should-fix)
the type of the repeated binding was found by checking a synthesized read of it, which gave `recursive_borrow` at
different lines in the two compilers. Fixes: the count runs on the statement before its temporaries are bound (so the
example above is now `try_position` too, conservative, G-LG15-1), and the declared type in scope is used. Both are
must_reject tests. The try_position message names the new cases, same text in both compilers.
