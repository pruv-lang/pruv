# L3 DB22: entry/req copy cuts and req host decode once

Base: 9bc98c01.

DB22 removes the five audit copies of D-DB18-3 (P1-P5) by reading or cutting from the existing pool by span. The req
host decodes the packet pool once per packet (D-DB20-2). A req mutant covers the exact `l0` check (D-DB20-3).
Accepted output is unchanged: no new output bytes, the same header, slots, padding and refusals (tests below).

## What DB22 does

- P1, `lib/ent_dispatch.pruv` `list_recipe`: the whole source pool was copied byte by byte with `append_span` before
  one title was cut to 200 units. It is now `ent_value::copy_pool_prefix` (word copy into the empty destination; the
  same `nu = clamp(nu, nb)`, `nb` and last-word padding).
- P2, `lib/entry_api.pruv` `index_begin_checked`: the ID table is no longer cloned. Each slot is read and rewritten in
  place (the body of `append_slot` inlined: the same offset and length clamps, `span_units` and start after a
  separator).
- P3, `lib/ent_bound.pruv`: each key was encoded into a temp pool (`encode_pool`) and appended with `append_span`. The
  new `ent_value::append_units` encodes the units straight into the key pool, with the same separator rule and header.
  It is exact for keys of at most 16,777,216 units; `ent_bound` caps every key at 16,000,000.
- P4, `req/req_list.pruv` `pack` / `blk`: the compact pool is built in place after the slots and size word, not copied
  again. A one-pass upper bound (`pack_bound`) sizes the block; `blk` truncates to the exact length. At the
  1,073,741,823 cap it falls back to the old exact two-pass length and refusal.
- P5, `req/req_fill.pruv` `title_head`: the 80-unit title no longer decodes the full source. It decodes 128-unit
  form-aligned parts (`ent_value::pstr_chunk_bytes` / `pstr_part`) and collapses and trims while streaming, into at
  most 82 units. The consumer reads only the first 81 units, which are the same as `trim(collapse(full))`.
- D-DB20-2, `req/leaf.rs` and `req/host/src/lib.rs`: string slots read a `LazyPool`. The pool is decoded and checked
  at the first string read of the packet and the result (or its error) is reused for every later slot. The first
  decode happens where the old per-slot decode first happened, so the refusal order and messages are unchanged.
- D-DB20-3, `req/q_mutants.py` M17 (`l0 !=` to `l0 <` in `lib/ent_wire.pruv`): probes F62 (completion pool with an
  extra zero word) and F64 (begin pool with an extra zero word) from `req/forge_test.py`. A probe kills the mutant
  only when the core returns a well-formed packet that accepts the forgery. Malformed core output counts as `other`.

## Audit and fixes

Audit: Codex gpt-6.2-astra ultra, once, over the whole diff.

- Must-fix (fixed): the first version decoded the pool eagerly at the top of `serve_call`. A call that never reads a
  string (for example code 30 with an empty pool section) was then refused with `pool header is truncated`, where
  the old code accepted it. Code 11 with a missing argument gave the pool error instead of `host call argument
  missing`. Fix: `LazyPool` decodes at the first string read (above).
- Should-fix (fixed): `append_units` comment now states the 16,777,216-unit limit of the equivalence.
- Should-fix (fixed): the M17 runner counted any explicit-reject failure as a kill, including malformed core output.
  `core_refused` / `begin_pool` now have a `verdict` mode (`refused` / `accepted` / `other`) and only `accepted`
  kills.
- Note (kept): when the slot length sum saturates, `pack` returns an empty block but `pack_bound` still counts the
  saturated sum for the reservation. Output bytes are the same; only the reserved bound is larger on that refused
  branch.

Recheck (Codex gpt-6.2-astra ultra, once, over the two fixes): the `LazyPool` fix is OK (the same string read points
and argument check order as 9bc98c01 on every call branch; at most one decode per `serve_call`, success and error both
cached). The verdict fix still counted a packet of kind 0 with no sections as `accepted`. Fixed: `verdict` now needs a
well-formed packet (`forge_test.well_formed`: header, non-zero kind, at least one section, a section table that fits)
for `accepted` or `refused`; anything else is `other`. No second recheck (the audit budget is one audit plus one
recheck); M17 was rerun after this change (tests below).

## Performance

`entry/perf_r02.py` cell `bound_session_index`, 15 rounds alternating with a 9bc98c01 checkout (same machine, same
window); value = median of the per-round pruv / hand ratios. `req/perf_req.py --no-node --sizes 1000,5000`, 3 rounds
alternating with the base; value = median per row, then the mean of the rows, as DB22 / base. Load average (1 / 5 /
15 min): 6.83 / 15.85 / 20.30 at the start, 5.27-8.66 / 12.77-13.97 / 17.69-19.2 during the rounds and at the end.

Entry time is better than DB20 and than the base in this window, but still above 1.0. Entry RSS is a fixed offset
above the base: pruv median 4,112,384 vs 4,030,464 bytes (M) and 8,765,440 vs 8,667,136 (L); hand medians are the
same. The harness binaries are the same size (1,240,824 bytes) and the generated Rust of P3 has no extra copy or
allocation (`append_units` writes into `key_pool` through `&mut`, on a borrowed slice of `keys`), so the cause is not
found (D-DB22-1). Req time and RSS are within the noise of the base (the plain sum over rows gave 1.150 because of a few outlier rows under load; the per-row median gives 1.010). Req was not re-measured against hand, so the DB20 0.931 is held only through the ratio to the base.
