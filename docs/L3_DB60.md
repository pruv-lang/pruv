# L3 DB60: claude owned jstr decodes (lib), lib user reruns, perf old/new/hand

Brief: (1) G-DB56-2, move claude onto `bench/l3/pkgs` if possible, otherwise keep `bench/l3/lib`, and switch claude's
five fresh-local decode sites to the DB56 owned decodes; `copy` stays only where a move is impossible. (2) G-DB56-8,
rerun the claude, qwen, json, supervisor and mcp suites and grok `test_impl --no-ts` (G-LG35-2) on the final sources,
all four pairs. (3) claude M/L old (main b5b80921) vs new vs hand on all four pairs. Base: main b5b80921. One release
`pruvc-rs` build in the worktree; no compiler, runtime, stdlib, pkgs, fixture or test change.

## pkgs or lib

claude stays on `bench/l3/lib` (its `json`, `jstr`, `lex`, `parse`, `lines`, `access` are symlinks into `../lib`).
A move to `bench/l3/pkgs` would need pkgs edits, which are out of this lane:

- `pkgs/access` has no `fields_into` (nor `hit`, `slot_error`, `fill_error`, `field_if_used`, `last_match` and the
  `find_ascii` prefilter, DB25/DB29/DB39); claude calls `fields_into` at `entry.pruv:220`, `entry.pruv:248` and
  `import.pruv:450`.
- `pkgs/parse` sizes the tape with DB55 `first_slots(n)` and `2*len+192`; `lib/parse` keeps DB39 `2*len+6` and
  `alloc(96)`. Switching would change claude's parse allocation profile, which needs its own perf check.
- `lex` and `json` are identical; `pkgs/jstr` only differs by `pub fn step`.

Recorded as G-DB60-1. The owned decodes were copied into lib instead (one copy each, same text as the pkgs twins).

## What landed

- `bench/l3/lib/jstr.pruv`: `string_text_owned(source, start, end)` and `owned_text(take data)`, the DB56
  `pkgs/jstr` functions with the same contracts: the decoded `[u8]` is checked with `utf8_valid` and moved into
  `str_from_utf8` instead of being copied through `utf8_to_string`.
- `bench/l3/lib/access.pruv`: `string_text_owned(doc, id)`, the `string_text` contract and body with the last call
  going to `jstr::string_text_owned`. `string_text` and `adapter_probe` are unchanged, so budget, entry and req (the
  other flat `--lib` users) compile the same code as before.
- claude call sites, `access::string_text` -> `access::string_text_owned`:
  - `entry.pruv:139` `string_field_of`
  - `entry.pruv:277` `string_content`
  - `import.pruv:470` `consume_entry_of`
  - `import.pruv:544` `read_window` model id
  - `time.pruv:361` `iso_of`

## Copies kept, and why

| `import.pruv:548` `read_window` | `model = copy(value)` on the `Decoded(value)` arm | same match-binding rule (G-DB59-1) |
| `import.pruv:309` | `adapter_probe(iso.text)` | a field; `owned_text(move iso.text)` is rejected (`foreign_move`, as `codex/list.pruv:50`) |
| `a1_root.pruv`, `a2_root.pruv`, `a3_root.pruv` `adapter_probe` (15 sites) | `adapter_probe(..)` | borrowed parameters or fields (`a.bytes`, `b.bytes`) whose length is read after the decode |

Reading:

- Allocated bytes and blocks never rise: new < old on 44 of 96 M/L cells and equal on the other 52 (head and tail
  do not reach the decode sites). The largest cut is long_text window, -44.0 MB (-28%) on all four pairs, which is
  the long string no longer copied by `utf8_to_string`. Blocks drop 10-48% on the window cells (turns16/17 -10% rust,
  -40% llvm; block_arrays llvm 242253 -> 2069).
- Window time drops 2-11% on turns16/17/200, window_8MiB and ring_wrap on all four pairs. long_text llvm is +4.6%
  and +6.1%, at 4.1-4.4 ms where rust pairs take 1.4-1.6 ms. That llvm/rust spread was there before DB60 (old 4.13-4.16
  vs 1.52-1.56) and is not from this change.
- Peak RSS moves by one or two 16 KiB pages either way on most cells (noise at this resolution). block_arrays window
  and long_text rs/llvm swing by up to +-1 MB in both directions between old and new; the allocation counts there
  fall, so this is read as RSS noise under load.
- Gate: no M/L cell family reaches 1.0x hand on every axis. Window time is 1.03-1.29x hand on turns16/17/200, window_8MiB and ring_wrap (block_arrays rust, long_text and depth_limit are below hand). long_text
  allocates 4.9x hand's bytes and window_8MiB 1.01x on rust pairs. On llvm pairs the interposer sees far fewer bytes
  than hand (turns17 0.19 vs 0.39 MB, turns200 1.0 vs 4.4 MB). Not investigated here; old and new are comparable to
  each other, but the llvm-vs-hand allocs cells are not taken as a 1.0x pass.

## Audit

One review (Codex gpt-6.2-astra ultra) of the uncommitted diff: no must-fix. It checked the contracts against the
pkgs twins, the invalid-UTF-8 and non-string paths, behaviour at the five sites, the remaining `adapter_probe` and
copy sites, and the other lib users (budget, entry and req keep `string_text`). It also checked the generated a4
Rust (`String::from_utf8_unchecked` on the same `Vec<u8>`) and LLVM (pointer, length and capacity passed through).
Advisory, kept: in `--no-verify` builds `string_text_owned` checks UTF-8 twice (early return on failure, then the
conversion re-checks). The pkgs twin has the same shape and verified builds check once.
