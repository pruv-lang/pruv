# L3 LG26: exact UTF-8 model, `utf8_valid_span` prefixes of copied strings

Scope: G-LG25-1 and G-LG25-2 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is changed.
G-LG24-2, G-LG22-3, G-LG23-1, G-LG20-2/4/5, G-LG18-3, G-LG15-1, G-LG16-1 and G-LG21-x are out of scope and unchanged.

Status: LG26: G-LG25-1 closed (a `[u8]` buffer filled by copying whole `str` values carries `utf8_valid_span(buf, 0, k)` as a loop invariant and contract; the verifier models UTF-8 exactly and assumes valid `str` values in functions that use UTF-8 facts, so a later `subview` of the proven prefix is passed as a `str` with no run-time UTF-8 or boundary check, both compilers; replacing the bench/l3/codex `span_ok` check is bench work, outside this lane)
Status: LG26: G-LG25-2 open (array/`Vec` element invariants not done: carrying the quantified element clause through loops is a loop frame analysis, see G-LG26-1)

## What landed

- Exact UTF-8 model (R-6b-3, SPEC.md 6b). `utf8_valid(b)` was `ascii(b) || utf8_valid!(b)` with an uninterpreted
  `utf8_valid!`. It is now one quantified formula `W(b, lo, n)`: every byte of the window is ASCII, a lead byte whose
  continuation bytes (with the first-continuation limits for `E0`, `ED`, `F0`, `F4`) follow inside the window, or a
  continuation byte that completes a lead byte one to three bytes before it inside the window. It is Rust
  `str::from_utf8` validity, so assuming it and proving it are both sound. The LG9 ASCII fact is its first disjunct.
  The LG25 `[u8]`-to-`str` view obligation keeps its shape and gets the new encoding.
- `utf8_valid_span(b, lo, hi)` (contracts only, `[u8]` argument): `0 <= lo <= hi <= len(b)` and `W(b, lo, hi - lo)`.
  In code it is `type/contract_only`; a `str` or other array argument is `type/type_mismatch`; the name is reserved.
  A `requires` checked at run time (`--no-verify`) evaluates it as the range test and `str::from_utf8(&b[lo..hi])`
  (Rust) or `pruv_utf8_valid` on the advanced pointer (LLVM); proof mode emits nothing.
- Valid `str` values. In a function that uses UTF-8 facts (its body or contracts call `utf8_valid`,
  `utf8_valid_span` or `str_from_utf8`, pass a `[u8]` `subview` to a `str` parameter, or call a user function whose
  contracts mention `utf8_valid` or `utf8_valid_span`) the verifier assumes `W(s, 0, len(s))` for `str` parameters,
  `str` call results, `str` field reads, string literals, and `substr`, `copy` and `str_from_utf8` results. Other
  functions get no new assumption.
- Generated code: the verified Rust of `tests/runtime/lg26_utf8_span` passes `subview(buf, 0, k)` to `str`
  parameters as `str::from_utf8_unchecked((&buf).get_unchecked(0..k))` and has no `from_utf8(` call; the
  `--no-verify` Rust has three (the two view checks and the `requires` check of `append`).
- Array and `Vec` element invariants (G-LG25-2): not implemented (see the rule decision and G-LG26-1).

## Rule decisions

- Exact formula, not a ghost type state. G-LG25-1 offered a loop invariant form or a ghost UTF-8 fact on `[u8]`. A
  contract predicate over a byte window needs no new type state and no layout change: the facts live in invariants
  and `ensures`, like the other array facts. It only works if the model knows that a valid prefix followed by a valid
  string is valid, which the uninterpreted `utf8_valid!` could not give, so the model became exact. With the exact
  window formula the solver derives concatenation and boundary facts byte by byte (each byte of the result is
  covered by the window it came from; a continuation byte at the start of the second part cannot occur because that
  part is itself valid).
- `str` validity is assumed only where UTF-8 facts are used. Assuming `W` for every `str` everywhere would add a
  quantifier to every function that touches a string and change proofs and timing of programs that never mention
  UTF-8. Gating on the function's own use of UTF-8 facts keeps every other obligation the same.
- Copy invariants are stated over buffer indices: `forall t in k..k + j: buf[t] == s[t - k]`. The offset form
  `forall t in 0..j: buf[k + t] == s[t]` is the same fact, but the solver cannot match a goal byte `buf[i]` against
  `buf[k + t]`, and the `ensures utf8_valid_span(buf, 0, k + len(s))` of the append helper timed out with it. SPEC.md
  states the form.
- `--no-verify` checks the predicate. A `requires` with `utf8_valid_span` is part of the safe-mode entry check like
  `utf8_valid`, so it is lowered (range test first, so the slice cannot panic) instead of being dropped. Programs that
  do not use the name produce the same output as before.
- Codes: proving a span or a `str` view from a copied prefix fails as `utf8_invalid` (view) or `ensures`/`requires`
  (contract), the codes of the existing obligations, so no new error code.
- Element invariants (G-LG25-2): not attempted. The clause `forall i in 0..len(a): (!g || C[a[i]])` must survive
  loops that write the array (`a[i] = x`, `a[i].f = x`, `push`), which keep only user or inferred invariants today.
  Carrying it is a loop frame analysis (which element clauses a loop preserves, and the in-place field-write case),
  a new analysis, so per the brief the step stops here and records the rule as G-LG26-1.

## Gaps

| Id | Gap |
|---|---|
| G-LG26-1 | Invariants of structs that are array or `Vec` elements are still not assumed or checked (was G-LG25-2, G-LG24-1). Rule: the element clause `forall i in 0..len(a): (!g || C[a[i]])` is assumed at entry and for reads, and checked where an element or the whole array leaves the function. It cannot be enabled without a loop frame: a loop that writes the array keeps only stated invariants, so the clause is lost at the loop head and accepted programs would be rejected. The frame must decide which element clauses a loop preserves (unwritten indices keep it; written elements and `a[i].f = x` field writes re-prove it) and add them to the loop head; measure a0-a4 with it (at most +20%) before landing. |
| G-LG26-2 | Only `str` parameters, `str` variables, `str` field reads and `str` call results are assumed to be valid UTF-8 (W). The `str` produced by `string_to_str` gets no W in either compiler, so a `[u8]` buffer filled from it cannot be proved `utf8_valid_span` and its view is rejected. This is a missed accept, not an unsound one. Rule: assume W on the result, with the same gating. |
| G-LG26-3 | Performance: in a UTF-8-aware function the Rust verifier assumes W again on every read of a `str` variable, not only after loop havoc. Python does the same since the audit fix. Each W is a quantified clause, so a function that reads a `str` many times adds many equal clauses. a0-a4 do not use UTF-8 facts and are not affected (see Timing). Rule: assume W once per SSA value or after havoc only. |
