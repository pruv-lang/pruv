# L3 LG17: invariant structs in legacy mode, `move` of a `str` local, slice copy in `ev_proc_read`

Scope: G-LG16-2, G-DB28-2 and G-DB28-1. Both compilers (Python `pruvc/`, Rust `pruvc-rs/`) change with the same
rejects, messages and output. No `bench/` fragment is changed and codex is not ported to the new `str` move.

Status: LG17: G-LG16-2 closed (legacy mode rejects any function taking an invariant struct parameter, `type/entry_signature`)
Status: LG17: G-DB28-2 closed (`text = move t` for a `str` local, ownership checked like arrays, both compilers and backends)
Status: LG17: G-DB28-1 closed (`ev_proc_read` copies the two `as_slices` halves with `extend_from_slice`, both backends)

## What landed

- Legacy rule (G-LG16-2). A file without `pub fn` (legacy single-file mode) exposes every function to the host, and
  no host caller is verified. So in that mode every function that is not a `pred` and not `foreign` is rejected with
  `type/entry_signature` ("host entry F cannot take parameter P of struct S with an invariant") if a parameter
  (plain or `inout`) has an invariant struct type. This is the explicit-mode host-entry rule applied to all
  functions; it is the smallest sound rule because the verifier assumes `INV[p]` at the entry of every such
  function. Returning an invariant struct stays allowed (the callee proves it). A program that needs internal
  functions over invariant structs uses explicit mode. Nested positions (fields, elements, `Option` payloads) were
  never assumed, so they need no rule. No `tests/` or `bench/` program outside LG16/LG17 was rejected by it; the LG16
  tests that used legacy mode now declare one `pub fn` (`lg16_inv_basic`, `lg16_inv_store`,
  `lg16_inv_contract_call`, `lg16_inv_call_arg`, `lg16_inv_inout_arg`, `lg16_inv_inout_exit`,
  `lg16_inv_quant_name`).
- `str` move (G-DB28-2). `move t` of a `str` local is an allowed array source, so `text = move t` (and
  `let u: str = move t`, a struct field `S { f: move t }`) type-checks. `str` lets are tracked by the ownership pass
  like arrays: a later read of `t`, also in an `assert`, loop `invariant` or `decreases` clause, is
  `type/foreign_move` ("use after move"), a move inside a loop body that does not restore `t`
  is `type/foreign_loop_move`, and moving a borrowed `str` parameter is `type/array_alias`. The Rust backend emits a
  plain move (`text = t;`); the LLVM backend empties the moved slot as for arrays, so the value is freed once.
- `ev_proc_read` (G-DB28-1). The compiler-emitted effect runtime copied child output from the `VecDeque` into the
  line buffer with `extend(drain(..n))`, byte by byte. It now copies `front[..first]` and `back[..n - first]` from
  `as_slices()` with `extend_from_slice` and then drops `drain(..n)`. The LLVM backend calls the same emitted Rust
  runtime through the foreign shim, so both backends change.
- SPEC.md: section 6a (legacy rule) and 6b (`str` move).
- Tests: `tests/must_reject/lg17_inv_legacy_param`, `lg17_inv_legacy_inout`, `lg17_str_move_after`,
  `lg17_str_move_param`, `lg17_str_move_loop`, `lg17_str_move_assert`; `tests/runtime/lg17_str_move` (verified, `--no-verify`,
  `--trust-callers`, Rust and LLVM).
- Runs: `run_all --backend both` passes 4949/4949 with the Python compiler and 4961/4961 with the Rust compiler;
  `cargo test --release` passes; `diff_rust.py --fuzz-count 20` reports all same; `--only g8_frontend` passes on both.
  Old-vs-new output compare: 5122 of 5364 jobs byte-identical, the 242 diffs are only the `ev_proc_read` lines.

## Gaps

No new gap was found. A `take` parameter of type `str` stays rejected by design (`type/foreign_move`); SPEC 6b now
says so.
