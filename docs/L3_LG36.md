# L3 LG36: str payload binders of a consuming match are owned on both compilers, no move under an enclosing arm

Scope: G-DB59-1 (pruvc-rs rejects `move x` of the `str` binder in codex `str_at`), G-LG35-1 (an explicit `move` of a
payload binder while an enclosing match arm borrows the same owner), G-LG35-4 (`cargo test --release`). Base: main
b5b80921. Bench source edited: `bench/l3/codex/util.pruv` `str_at` only. No older L3 doc was edited.

Status: LG36: G-DB59-1 closed (both compilers track the `str` binders of a consuming match as owned; `str_at` is `return move x`, no `.clone()` in the generated Rust)
Status: LG36: G-LG35-1 closed (a `move` of a payload binder whose owner an enclosing arm borrows is rejected on both compilers, `array_alias`)
Status: LG36: G-LG35-4 closed (base `cargo test --release`: 150 passed, 0 failed; after the last fix: 150 passed, 0 failed)

## Step 1: owned `str` binders (G-DB59-1)

Root cause: the foreign ownership pass of both compilers registers the payload binders of a consuming match (the
owner is a local enum that is dead after the match) as live owners only when the field is an array
(`pruvc/foreign.py` consuming-match `srcs`, `pruvc-rs/crates/pruv-core/src/foreign.rs` the same list). pruvc py still
accepted `move x` of a `str` binder because its `mv` did not ask whether the name was tracked; pruvc-rs did ask, so an
untracked `str` binder fell to the borrowed-parameter rule (`foreign_move`). The fix adds `str` fields to the `srcs`
filter on both compilers. A registered binder gets the ordinary owner rules: the branch join keeps "maybe moved", a
move inside a loop must be restored before the next iteration, and a later arm binder of the same name starts live
again. A first attempt that only widened the pruvc-rs `mv` test (array or `str`) was reverted: the review showed that
an unregistered binder loses its moved state at a branch join and in a loop, and its dead state leaks into a later
arm binder of the same name (MUST-FIX, D-LG36-3).

Emission: `return copy(x)` of the last use was already emitted as a move on Rust (last-use copy elision), so DB59's
"one `.clone()`" was wrong and the codex Rust and bindings are byte-identical old vs new. On LLVM `return move x` now
hands the payload over: the `Decoded` arm of `str_at` gains one `getelementptr` and one
`store { ptr, i64, i64 } zeroinitializer` into the `Text` payload field, so the owner's cleanup frees null. The
`pruv_free` / `pruv_copy` call counts of the codex LLVM are the same (481 / 37).

Tests: `tests/runtime/lg36_rt_binder_own` (both backends, allocation balance): `str_take` (move of a `str` binder),
`other_owner`, `after_close`, `reuse_name` (two matches with the same binder name, the first binder moved, the second
starts live); `gen_absent` `.clone()`, `llvm_fn_absent` `@pruv_copy(` in `reuse_name`.
`tests/must_reject/lg36_str_move_branch_read` (move in one branch, read after the join: `foreign_move`),
`tests/must_reject/lg36_str_move_in_loop` (move inside a loop of the arm: `foreign_loop_move`).

## Step 2: no move under an enclosing arm (G-LG35-1)

`movable_scrut` (`pruvc/check.py`, `pruvc-rs/crates/pruv-core/src/check.rs`) now also requires that no enclosing
match arm borrows the scrutinee root (`active_roots`). An inner consuming match on an owner whose outer arm is still
open keeps its binders borrowed, so an explicit `move` of such a binder is rejected (`array_alias`) on both compilers,
and the LLVM generator can no longer empty a field the outer binder still views.

Tests: `tests/must_reject/lg36_move_under_outer_arm` (array binder), `tests/must_reject/lg36_str_move_under_outer_arm`
(`str` binder); the positive cases are `other_owner` and `after_close` of `tests/runtime/lg36_rt_binder_own` (the
inner owner is different, or the outer arm has closed).

SPEC.md R-6e-12a documents both rules and links the five tests.
