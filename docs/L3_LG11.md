# L3 LG11: the `?` operator and owned `String` errors (E2)

Scope: the `?` operator (closes G-LG10-1) and step E2 of the error-handling key point in `docs/LANG_ROADMAP.md`.
Both compilers (Python `pruvc/`, Rust `pruvc-rs/`) change with the same semantics and diagnostics. No `bench/`
fragment is changed.

Status: LG11: G-LG10-1 closed (`?` in front end, proof, Rust and LLVM output); E2 owned `String` errors landed in front end, proof and Rust output; LLVM keeps the LG10 reject for E != `i64` (G-LG10-2, G-LG11-2).

## What landed

- `?` syntax (SPEC.md §6c "The `?` operator"). Postfix `e?` binds like a call or index suffix. It is allowed only
  as the whole right-hand side of `let [mut] x: T = e?;`, of an assignment to a local `x = e?;`, or of an expression
  statement `e?;`. Anywhere else (nested in an expression, a condition, a return value, a contract, a `par` member,
  an index or field assignment) it is rejected with `type/try_position`.
- `?` typing. The operand must be a `Result<U, E>` (`type/try_operand`), the enclosing function must return a
  `Result<T, E'>` (`type/try_return`), and E must equal E' exactly; there is no conversion (`type/try_error_type`).
- `?` meaning. The checker lowers the statement and the rest of its block into the existing `match`:
  `match e { Ok(__pruv_try_vN) => { <stmt with __pruv_try_vN>; <rest> } Err(__pruv_try_eN) => { return
  Err::<T, E'>(__pruv_try_eN); } }`, N a per-function counter. Proof, Rust output and LLVM output therefore see
  exactly the explicit `match` + `return Err` form; no new proof rule exists. Programs without `?` are unchanged.
- LLVM. `?` works for E = `i64` (it is an ordinary match); other E keep the LG10 `codegen/unsupported_type`.
- E2 owned `String` errors (SPEC.md §6c "Owned `String` errors"). `Result<T, String>` is allowed as an error type.
  The Result owns the String: matching consumes the scrutinee, the `Err(s)` binder owns the String and is consumed by
  `string_to_str`, by passing it to a `take` parameter or by building another `Err`; a use after such a move is
  `own/use_after_move`. `err_val(result)` in contracts reads the String (e.g. `len(err_val(result)) > 0`).
  Proof stores the Err payload with the existing String buffer sort; Rust output types it as `::std::string::String` (runtime and
  contract), clones it into contracts and passes a borrowed Result parameter as `&Result<.., String>`.
- `type/result_error_type` now reads "<type> is not supported as a Result error type", fix "use i64, bool, String
  or a value struct or enum". `str`, arrays, collections, records holding buffers (E3), Option, Result, `u8`, unit
  and type parameters stay rejected.

## New gaps

| Id | Gap |
|---|---|
| G-LG11-1 | `?` is only a statement-level form; `return f()?;`, `g(f()?)` and `if f()? {` are rejected (`type/try_position`) and need a `let` first. |
| G-LG11-2 | The LLVM backend does not lay out `Result<T, String>`; such programs keep `codegen/unsupported_type` (samples in `tests/llvm_pending.txt`). |
| G-LG11-3 | `String` is allowed only on the Err side; `Result<String, E>` (owned Ok payload) is still rejected. |
| G-LG11-4 | The test runner checks drop balance (`g6_drop_balance`) only on LLVM runs, so the Rust-only E2 samples have no drop-balance measurement. |
| G-LG11-5 | `?` diagnostics point at the statement, not at the `?` token; both compilers agree. |
| G-LG11-6 | A contract that reads a `String` binder after it moved (`Err(e) => { return string_to_str(e); }` then `assert len(e) > 0`) is accepted by both compilers; proof clauses do not check String moves. |
| G-LG11-7 | The Python compiler hits `RecursionError` on very long chains of flat `?` statements (512 in a row), because each `?` nests the rest of the block; the Rust compiler accepts them (the known `py_recursion` class of `tests/diff_rust.py`). |
| G-LG11-8 | Diagnostic-only differences between the compilers on rejected programs: `?` in a `par` member (Python `type/try_position`, Rust `parse/parallel_syntax`), `?` in a `pred fn` return (`type/try_position` vs `type/pred_signature`), `?` after `for (k, v) in S {}` (the parsers split it differently), `cost 0?` (diagnostics in another order). |
| G-LG11-9 | An unreachable `Err(s)` that moves a borrowed `s` is `type/foreign_move` in Python and `type/foreign_borrow` in Rust; both reject. |
| G-LG11-10 | A `cost` function that calls another `cost` function with `move r` of a `Result<_, String>` gets a caller-side cost call that differs: Python passes `&pruv_cost_arg_0`, Rust passes `pruv_cost_arg_0` (a type error in the generated Rust). The fix is in Rust `codegen.rs` (caller-side `__pruv_cost` arguments) and was left out of LG11's build budget. |

G-LG10-2 (LLVM layout for E != `i64`) and G-LG10-3 (`unused_parens`) stay open.

## Tests

New runtime samples `tests/runtime/lg11_try_i64` (both backends), `lg11_try_struct` and `lg11_e2_string` (Rust
backend, LLVM-pending). New must_reject samples `tests/must_reject/lg11_try_{position,operand,fn_not_result,
err_mismatch}` (`type/try_*`), `lg11_try_false_ensures` (`verify/ensures` on the early `Err` return) and
`lg11_e2_use_after_move` (`own/use_after_move` on a String error binder). `tests/must_reject/lg10_err_string` now
uses `Result<i64, str>`, which stays rejected. The `g3` and other `lg10` tests are unchanged.
`tests/run_all_rows.txt` gains 24 lg11 rows and nothing else.

Audit fixes (after the first review): the owned String error is spelled `::std::string::String` in both compilers
(type, `Ok/Err::<T, E>` constructors and contract type); Rust contract conversion of `Result<T, String>` no longer adds
an identity `.map_err(|v| v)` and Python clones as `x.clone()`, so the outputs are the same; the Rust `cost` call at function entry
passes `&r` for a `take r: Result<_, String>` (the caller side is G-LG11-10); a contract `len(err_val(r))` on a String
error is emitted without extra parentheses in Python, as Rust does; Rust rejects `==` on `Result<_, String>` (`type/eq_type`) and checks a contract
read of an owned Result after `move` (`type/foreign_move`), as Python does.

Checks on the final tree:

- lg11 runtime 18/18 and must_reject 6/6, lg10 runtime 32/32 and must_reject 9/9, g3 runtime 140/140 and
  must_reject 64/64, each with both compilers (rerun after the audit fixes).
- `tests/run_all.py --backend both`: Rust compiler 4838/4838; Python compiler 4826/4826 (the 12 extra Rust rows are the Rust-only `g8_frontend` cases). These full runs started during the audit fixes; the lg11 groups above were rerun on the final tree.
- `g8_frontend`: Python 27/27, Rust 39/39. `cargo test --release`: 150 passed (before the audit fixes; not rerun).
- `tests/diff_rust.py --fuzz-count 20`: 26007/26007 cases the same (after the audit fixes).
- Old vs new output on all 2622 `tests/**/*.pruv` programs except `lg11*`, both compilers, both backends: byte-identical
  with `--no-verify` (1722 Rust and 1595 LLVM outputs per compiler) and with verification (1050 Rust and 943 LLVM)
  before the audit fixes; after them, the 485 programs that use `Result`, `String` or `cost` are again byte-identical
  with `--no-verify`.
