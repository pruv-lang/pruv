# L3 LG27: W once per `str` value, W on `string_to_str`, `Vec` element invariants

Scope: G-LG26-3, G-LG26-2 and G-LG26-1 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is
changed. G-LG24-2, G-LG22-3, G-LG23-1, G-LG20-2/4/5, G-LG18-3, G-LG15-1, G-LG16-1, G-LG21-x, G-DB30-2 and
G-DB33-1/2 are out of scope and unchanged.

Status: LG27: G-LG26-3 closed (the UTF-8 clause W of a `str` value is assumed once per SSA value and again only after loop havoc, both compilers; the fact keeps its path guard, except in the contract domain check (G-LG27-7); on the lg25/lg26 tests the asserted clauses drop by 3-33% and the SMT text by 5-65%, the query count is unchanged and no test flips)
Status: LG27: G-LG26-2 closed (the `str` result of `string_to_str` is assumed valid UTF-8 under the same gating, both compilers; tests/runtime/lg27_string_to_str_w)
Status: LG27: G-LG26-1 partial (a top-level `Vec<T>` parameter or result, T reaching an invariant struct, carries `forall i in 0..len(v): C[v[i]]`: assumed at entry, proved at call arguments, the result and inout exit, both compilers; a local `Vec` built in a loop needs a user loop invariant (G-LG27-1); arrays, nested `Vec`, `Option`/`Result`-wrapped `Vec` and `HashMap` values are not covered (G-LG27-2); `a[i].f = x` is not parsed (G-LG27-3))

## What landed

- W once per value (G-LG26-3). In a UTF-8-aware function the verifier assumed `W(s, 0, len(s))` again on every read
  of a `str`. The assumption is now recorded in the state's set of observed fact ids (`obs`, the set the G9
  recursive-value facts use; it is copied with the state at forks) and skipped when the same term was already
  assumed. A loop havoc makes a new term, so the havocked value is assumed again on its next read. The fact is
  `Implies(And(g), W)` with the path guard g of the read (inside a `ForAll` under a quantifier), so a read under a
  short-circuit guard such as `false && f(subview(b, 0, 1)) == 1` does not leak W of b to the rest of the path.
- W on `string_to_str` (G-LG26-2). The `str` result of `string_to_str` goes through the same assumption as other
  `str` call results, with the same gating (only in functions that use UTF-8 facts).
- `Vec` element invariants (G-LG26-1, SPEC.md 6a). For a parameter or result whose type is exactly `Vec<T>`, T
  reaching a struct with an `invariant`, every effective clause of T (the same list as for a T parameter) becomes
  `forall $inv_e in 0..len(p): C[p[$inv_e]]`, with the path guards inside the quantifier. It is a synthesized
  `requires` for each such parameter (assumed at entry, proved at every call argument) and a synthesized `ensures`
  for the result and inout parameters. The label is `p[]` plus the field path, so a failure reads
  `invariant of crate::R (line 4) for result[]` or `... for parameter v[] of crate::first`. A user quantifier named
  `$inv_e` inside a clause is renamed, and in an element clause a user variable that would become `$inv_e`
  gets a `_bound` suffix so it does not capture the element index. A `result` parameter of type `Vec<P>`, P with
  an invariant, is rejected at declaration (`type/invariant_decl`), as for a `P` parameter.

## Rule decisions

- Step 1 (G-LG26-3): dedupe through `obs`, not a new cache. The observed-fact set is already per state, copied at
  forks and dropped with the branch, so a fact skipped on one path was assumed on that same path. A havocked
  variable is a fresh term with a fresh id, which gives "again after loop havoc" with no extra code. The key is the
  guarded fact, not the bare W: the first audit found that the bare W pushed under a short-circuit guard leaked to
  the rest of the path, so the guard is kept and the same value read under a different guard is assumed again.
  Both compilers build the same guarded term, so the traces stay equal.
- Step 2 (G-LG26-2): `string_to_str` returns a Rust `&str` of a `String`, which is valid UTF-8 by construction, so
  assuming W is sound. It takes the existing call-result path and gating; no new code path.
- Step 3 (G-LG26-1): only the top-level `Vec<T>` of a parameter or result. A read-only `Vec` parameter cannot be
  written, so its entry fact holds in every loop and the G-LG26-1 loop frame is not needed for it. An inout `Vec`
  the body changes (`vec_at_mut`, `vec_clear`, ...) is proved at exit; a loop that changes it needs a user loop
  invariant stating the element clause, like a local `Vec` built in a loop (G-LG27-1). Host entries already reject
  `Vec<struct>` parameters (the per-mode wording is G-LG27-6), and arrays cannot hold structs, so no host or
  array change. A local `Vec` built by
  pushes in a loop still loses the clause at the loop head unless the program states it as a loop invariant; the
  automatic loop-head clause is a loop frame analysis, a new analysis, so it stops here (G-LG27-1). A research pass
  found no test or bench program that passes or returns a `Vec` of an invariant struct, and none flipped.
- Codes: an element clause fails as `verify/struct_invariant`, the code of the existing invariant obligations.

## Gaps

| Id | Gap |
|---|---|
| G-LG27-1 | A local `Vec<S>` built in a loop (pushes) loses the element clause at the loop head unless the program states `forall j in 0..len(w): ...` as a loop invariant. Rule: a loop frame adds the element clause of every `Vec` the loop only pushes clause-proved values to (and re-proves it after the loop). It is the loop frame analysis of G-LG26-1. |
| G-LG27-2 | Element invariants are only for a top-level `Vec<T>` parameter or result. A `Vec` inside a struct field or enum payload, a `Vec` of `Vec`, an `Option<Vec<S>>`/`Result<Vec<S>, E>`, and `HashMap` values carry nothing. Rule: extend the invariant path with an element step under the existing guards, assumed and proved where the outer value is. |
| G-LG27-3 | `a[i].f = x` (a field store into an element) is not parsed, so in-place element updates must rebuild the struct. When it is added, the element clause of that index must be re-proved at the store. |
| G-LG27-4 | A generic function with a `Vec<T>` parameter is not `parametric_safe` (LG24: `Vec` is not a walked position), so at a call with T an invariant struct the instantiated element `ensures` of the result is not assumed (the instantiated element `requires` of the arguments are still proved). A missed accept, not an unsound one. Rule: treat a top-level `Vec<T>` as a walked position in `parametric_safe`, after showing the parametric body cannot build a `Vec<T>` element that is not one of its inputs. |
| G-LG27-5 | On the first read of a `str` parameter W is registered twice (once at entry, once as the read's guarded fact under the read's guard), so a guarded read adds one more clause than needed. Sound, only cost. Rule: register the entry W unguarded in `obs` under the guarded key too, or skip the read fact when the entry fact is in `obs`. |
| G-LG27-6 | The wording "host entries already reject `Vec<struct>` parameters" (this doc, SPEC.md 6a) is one sentence for every build mode, but the entry-signature rules differ by mode. Rule: state per mode which entries reject a `Vec` of an invariant struct, from `check_entries`. Wording only, no code. |
| G-LG27-7 | The contract domain check (`dom`, `pruvc/verify.py` and `symbolic.rs`) evaluates the right side of `&&`, `||` and `==>` with the outer guard g only, not g plus the left side, so a `str` read there (e.g. `requires false ==> 1 / len(p.label) == 0`) adds its W under g instead of under the short-circuit guard. Only the returned domain formula is wrapped in the guard. The ordinary expression path keeps the guard (`tests/must_reject/lg27_utf8_guard`). Found by the recheck audit after the last allowed build; LG26 pushed W unguarded on every read, so this path is not new. Rule: in both `dom` implementations pass `g + [l]` (`g + [Not(l)]` for `\|\|`) to the right-hand recursion, and add a must_reject test with a partial-character subview read under `false ==>` in a `requires`. |

## `g10a_r21_backpressure` (main CI diff_trace)

main CI failed diff_trace on `tests/runtime/g10a_r21_backpressure`: one obligation was `unknown` with "solver gave
up (timeout)" in Python and "incomplete quantifiers" in Rust. Cause: not an encoding difference. The SMT text of the
obligations is byte-identical in the two compilers, both use z3 5.3.3 with the same solver and timeout, and the
z3 command line answers `sat` on the dumped query. The obligations are the run-time `assert`s after the mode-0 echo
loop (the test runs with `--no-verify`, so they are not meant to be proved), decided under the byte quantifiers of
`socket`'s `payload` and of the loop's reads; there z3 answered `sat`, `unknown` (incomplete quantifiers) or timeout
depending on term creation order and load, so the result moved between runs and machines (main CI failed on it before
LG27). Fix:
the echo loop and the closing checks move to two functions taking the `Loop` (`echo`, `finish`), so those asserts
are decided without the quantifiers and z3 answers `sat` decisively in both compilers. The diff_trace rules are
unchanged. Checked: `tests/diff_trace.py --only input` on that file, 3 runs, `cex_only` each; the runtime row
passes 4/4 (both backends, both flag sets) in both compilers.
