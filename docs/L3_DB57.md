# L3 DB57: codex in-place grow_bytes, allocation trace, read_server_requests flake

Brief: (1) G-LG32-2, reapply D-DB52-1 (`grow_bytes` with `inout buf`, `buf = resize(buf, ...)`) now that the LLVM
backend lowers that assign to one realloc (LG32). (2) G-LG33-5, measure codex M/L old vs new on all four pairs and name
the next biggest copies on the read path. (3) G-LG29-4, find and fix the `read_server_requests` flake. Base: main
f7dd7978. One release `pruvc-rs` build; no compiler, runtime, package or test change.

## What landed

- `bench/l3/codex/util.pruv`: `grow_bytes(inout buf: [u8], needed, cap) -> () ! alloc`, body `buf = resize(buf, next, 0)`.
  Same `requires`; the ensures now speak of `buf` and `old(buf)` (`needed <= len(buf) <= cap`, the old prefix kept).
  `read.pruv:63` and `rpc.pruv:134` call it with `inout hb.data` / `inout line.data` instead of reassigning a returned copy.
- Emission (both checked on `root.pruv`, old vs new): Rust backend `buf.resize(n, 0)` on the `&mut Vec<u8>` (old: a
  fresh `Vec::with_capacity` plus `extend_from_slice` plus `resize`); LLVM backend `call @pruv_regrow_u8` (old:
  `@pruv_resize_u8`, a fresh block plus copy).
- `bench/l3/codex/fixtures/cases.json`: `read_server_requests` first page action gets `"await": 1`, so the fake server
  reads and logs the client's reply to server request 6 before it answers `thread/turns/list` (see G-LG29-4 below).

The live peak drops 0.49-0.52 MB at L (rs/rust 487,392 bytes, the other three 520,160-521,216 bytes) while the
allocated bytes barely move: the in-place grow still asks for the same sizes, but the old grow held the old and the new
block at once. The 4 L grows of the page buffer (1,966,080 bytes) are now realloc calls that stayed in place.

Big blocks (>= 16 KiB) by call site at L, new, after the in-place grow:

- 80 blocks, about 2.0 MB: two per page in the line read (`rpc::step`, inlined into `codex_read_wire`): one plain
  malloc and one `RawVec::reserve` per page line. The source path copies the received bytes into `chunk`
  (`rpc.pruv:117`) and then the line's bytes into `line.data` (`rpc.pruv:135`), so a page line passes through two
  copies; the block count alone does not fix which block is which. G-DB57-1.
- rs/llvm only: one 945,570-byte realloc in `l3_codex_root__pruv_abi_codex_read_wire__typed`: the ABI wrapper shrinks
  the output wire's capacity to its length after `truncate` (`read.pruv:254`); whether the allocator moves (copies) it
  is not shown. G-DB57-2.
- 5 zeroed blocks, 198,264 bytes (calloc), and the runtime reader's `VecDeque` (49,152 bytes): small.
