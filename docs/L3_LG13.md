# L3 LG13: `?` in expressions and LLVM `Result<T, String>` for every value T

Scope: wave 1 of `docs/LANG_ROADMAP.md` (typed errors and `?`, E1/E2). Both compilers (Python `pruvc/`, Rust
`pruvc-rs/`) change with the same output. No `bench/` fragment is changed.

Status: LG13: G-LG11-1 partial (`?` inside the value of a let, a local assignment, a return, an expression statement and an if condition; the positions that stay rejected are G-LG13-1..4)
Status: LG13: G-LG12-1 closed (LLVM `Result<T, String>` for every value T: i64, bool, value struct, value enum, Option of a value)
Status: LG13: G-LG12-4 open (not touched)
Status: LG13: G-LG12-5 open (not touched; the message is shared with the G9 runtime-requires rejection)

## What landed

- `?` in expression position (G-LG11-1 partial). In a `let` value, an assignment to a local, a `return` value, an
  expression statement or an `if` condition, `?` may stand anywhere inside the expression (`return Ok(f(x)? + 1);`,
  `g(f(x)?);`, `if f(x)? && x < 100 { .. }`, `let y: i64 = a + (f(a)? + f(b)?);`). The checker finds the first `?` in
  evaluation order (children left to right, then the node) and lowers the statement and the rest of its block to
  `match e { Ok(v) => { <statement with that e? replaced by v>; <rest> } Err(err) => { return Err::<U, E>(err); } }`,
  then repeats on the statement inside the Ok arm for the next `?`. So operands run left to right, the proof sees the
  same `match` as the hand-written form, and both backends compile it unchanged. A bare `e?;` drops the value as
  before. Both compilers use the same rules (Python `try_site` / `find_try`, Rust `find_try` / `kid_mut`) and emit
  the same Rust and LLVM text.
- A `?` stays `type/try_position` when lowering it first would change what runs or in what order: in the right
  operand of `&&` / `||` / `==>` (it would run although the operand is skipped), inside a quantifier, after a call,
  constructor, move, index, arithmetic, unary `-` or string literal evaluated before it in the same statement (that
  work, including a bounds check or an allocation, would run after the `?` instead of before, or be skipped on the
  error path), and when its operand passes an `inout` argument while the statement reads a local outside the operand
  (the read would move after the call). Only locals, non-string literals, field accesses, `!` and comparison or
  logical operators may come before a `?`; the rule is checked also inside a short-circuit operand that may be
  skipped. It also stays rejected in a
  `while` condition, a field or index assignment, an assignment through a reference and in contracts. The message
  names the allowed places; must_reject `lg11_try_position` (while condition), `lg13_try_and_right`,
  `lg13_try_after_call`, `lg13_try_after_index`, `lg13_try_inout_read`, `lg13_try_field_assign`.
- LLVM `Result<T, String>` for every value T (closes G-LG12-1). The layout stays `{ i1, L(T), ptr }`; the Ok payload
  is a plain value, so the drop path still frees only the String handle. The type filter (Python `_typed_result_in`
  / `_g6_type_ok`, Rust `typed_result_llvm_error` / `g6_type_ok`) now accepts a value struct, a value enum and
  `Option` of a value besides `i64` / `bool`; a T that is recursive or holds a buffer is already rejected by the
  checker (`type/type_argument`). The `codegen/unsupported_type` message for the remaining shapes now reads
  "supports only with a value Ok type (i64, bool, a value struct or enum, or an Option of one), outside records and
  other generic types". `tests/runtime/lg12_e2_struct_ok.pruv` left `tests/llvm_pending.txt`.

## Tests

- `tests/runtime/lg13_try_expr` (both backends, three flag sets): `?` in a return, a call argument, nested calls, a
  sum of several `?`, an if condition with `&&` on the left, a local assignment, and with a `String` error.
- `tests/runtime/lg13_e2_value_ok` (both backends): `Result<Pt, String>`, `Result<Shape, String>`,
  `Result<Option<i64>, String>` as result, `take` parameter, match scrutinee and `?` operand, with
  `g6_drop_balance`.
- `tests/runtime/lg12_e2_struct_ok` now also runs on LLVM.
- must_reject: `lg13_try_and_right`, `lg13_try_after_call`, `lg13_try_after_index` (bounds check before `?`),
  `lg13_try_inout_read` (`set(inout x)? + x`), `lg13_try_field_assign`; `lg11_try_position` now uses a
  `while` condition (its old `return Ok(half(x)? + 1)` is valid).

## Audit

One review (Codex gpt-6.2-astra, ultra) found six mandatory points. Fixed in both compilers: a bounds check, a moved
buffer, a constructor allocation evaluated before a `?` (now rejected by the rule above), and an `inout` read after
the call (now rejected). Kept as a documented restriction: `(false && b()) == x?` stays rejected (G-LG13-1). Recorded
as a gap: the predicate fn diagnostic difference (G-LG13-5).

One confirmation re-check (same model) found findings 1-4 closed in both compilers with no accept/reject difference
between them, and two new points that are recorded as G-LG13-6 and G-LG13-7 (the build budget was used up, so the
Rust checker could not be rebuilt for a fix in this stage).

## Gaps

| Id | Gap |
|---|---|
| G-LG13-1 | `?` after a call, constructor, move, index, arithmetic, unary `-` or string literal evaluated before it in the same statement (`Ok(g(x) + f(x)?)`, `Ok(a[0] + f(x)?)`, `a + f(x)? + f(y)?`) is `type/try_position`, also when that work sits in a short-circuit operand that may be skipped (`(false && b()) == x?`): lowering would need the earlier work bound to fresh locals first. |
| G-LG13-2 | `?` in the right operand of `&&` / `\|\|` / `==>` or inside a quantifier is `type/try_position`: lowering would need the short-circuit turned into nested `if`s. |
| G-LG13-3 | `?` in a `while` condition, a field or index assignment, an assignment through a reference or a contract is `type/try_position`. |
| G-LG13-4 | `?` whose operand passes an `inout` argument while the statement reads a local outside the operand is `type/try_position` (a read after the call would see the old value, a read before it would move after the call). |
| G-LG13-5 | In a predicate fn, `return x?` is `type/try_position` in Python but `type/pred_signature` in Rust (pre-existing order of the two checks; the old Python gives the same `try_position`). |
| G-LG13-6 | In a local assignment, the target and an `inout` argument inside a `?` operand are not checked against each other: `x = set(inout x)? + 1;` passes in both compilers, because the inout read rule counts only the right side and after lowering `inout_context` sees the call and the assignment in different statements. The lowered program is well defined (the call runs, then `x` is assigned), but the rule that rejects `x = set(inout x) + 1;` is bypassed. Fix: before lowering, reject a `?` whose operand passes the assignment target as `inout`. |
| G-LG13-7 | A quantifier evaluated before a `?` in the same statement (`return Ok(sum(i in 0..1: i) + Err::<i64>(7)?);`) is not marked impure, so it gives `type/contract_only` instead of `type/try_position` (same in both compilers). Fix: mark a quantifier node impure in `find_try`. |
