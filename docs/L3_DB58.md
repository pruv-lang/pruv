# L3 DB58: codex page-line read into `chunk`, Pruv read_server_requests 30 runs, perf old/new/hand

Brief: (1) G-DB57-1, a page line passes two copies on the read path; confirm from the generated code and cut it to at
most one with existing language features, inside bench/l3/codex. (2) G-DB57-4, 30 Pruv runs of
`read_server_requests` on one Rust and one LLVM pair on the already built runners. (3) G-LG33-5 / G-DB57-3, codex M/L
old (main f76a2591) vs new vs hand on all four pairs. Base: main f76a2591. One release `pruvc-rs` build in the worktree;
no compiler, runtime, package, fixture or test change.

## The two copies, from the generated code

Old `rpc::receive` (`rpc.pruv:113-121` at f76a2591), stdout branch:

```
q = ev_proc_read(move q, slot, 1, 65536);
if ev_ok(q) {
  let data: [u8] = ev_bytes(q);
  if len(data) <= 65536 { copy_range(inout chunk, 0, data, 0, len(data)); st[4] = len(data); st[2] = 0; }
}
```

Emission (py/rust `root_gen.rs`, py/llvm `root_gen.ll`, old and new checked on the built runners):

- `ev_proc_read` drains up to 65536 bytes from the runtime's per-stream `VecDeque` into the loop's own `l.buf`
  (`pruv_ev_read_queue(.., None)`: `l.buf.extend_from_slice(front/back)`).
- `ev_bytes(q)` is `l.buf.clone()` on the Rust backend and `call @pruv_copy_v2` (a fresh block plus memcpy) on LLVM:
  one heap block and one copy per read. This is the "plain malloc" big block of G-DB57-1.
- `copy_range` copies `data` into `chunk` (copy 2), then `copy_span(inout line.data, filled, chunk, begin, i)`
  (`rpc.pruv:133`) copies the line's bytes into `line.data` (copy 3), after `grow_bytes` regrows `line.data`.
- `rpc.pruv:82-85` moves the finished `line.data` into the document (`lines::parse_owned`) and leaves an
  empty buffer, so the next line's `grow_bytes` starts from empty: the `RawVec::reserve` big block of G-DB57-1 is
  that regrow, one per page line, and it is the block the document keeps.

So a page line crossed runtime queue -> `l.buf` -> `ev_bytes` block -> `chunk` -> `line.data`: four copies. Two of
the targets are fresh heap blocks: the `ev_bytes` block (one per non-empty read) and `line.data` (regrown from empty
per line, and possibly more than once when a line spans several reads). Tying DB57's two big blocks per page line to
`ev_bytes` and `grow_bytes` is an inference that fits the generated code; the trace did not separate call sites.

## What landed

- `bench/l3/codex/rpc.pruv` `receive`: the stdout read is now
  `q = ev_proc_read_into(move q, slot, 1, inout chunk, inout got); if ev_ok(q) { st[4] = got; st[2] = 0; }`.
  `ev_proc_read_into` (existing builtin, already used by `bench/l3/supervisor`) copies from the runtime queue
  straight into the caller's `chunk` (Rust `pruv_ev_read_into` -> `pruv_ev_read_queue(.., Some(dst))`,
  `dst[..n].copy_from_slice(front/back)`; LLVM `@..._ev_proc_read_into(ptr, slot, 1, %p.chunk.a, %p.chunk.n, %got)`).
  Its contract keeps `len(chunk)` and gives `0 <= got <= len(chunk) == 65536`, so the existing `st[4] <= 65536`
  invariant holds without the old `len(data) <= 65536` guard. Read size is unchanged (`len(chunk)` = 65536).
- The stderr read (`rpc.pruv:106-110`, `ev_bytes` into `tail_push`) is unchanged: it is not on the page path.
- `bench/l3/codex/flake_runs.py`: loops one case on the built `work/<pair>/runner` binaries against the fake
  app-server (TS run once as the reference), each run checked with `common.check_case` (expected result, TS result,
  TS request log, protocol violations). No rebuild or verify per run.

After the change a page line crosses runtime queue -> `chunk` -> `line.data`: two copies instead of four, and the
per-read `ev_bytes` block is gone. The step from the filled input buffer to the line buffer is one copy, the same as
hand Rust (`hand/reader.rs:29-30`: `BufReader` buffer -> `self.line` via `read_line`); where hand reads the pipe straight
into its `BufReader` buffer, Pruv's runtime reads into its queue and then copies queue -> `chunk` (one more copy,
runtime side, outside the lane). The difference left is reuse: hand clears and reuses
`self.line` (its capacity stays), while `parse_owned` takes `line.data` into the document, so Pruv allocates a fresh
line block per page line (G-DB58-1).
