# L3 LG24: struct invariants at generic call sites, in Err payloads and in generic enum variants

Scope: G-LG23-4, G-LG23-3 and G-LG23-2 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is
changed. G-LG22-3, G-LG23-1, G-LG20-2/4/5, G-LG18-3, G-LG15-1, G-LG16-1, G-LG21-x and G-DB32-1 are out of scope and
unchanged.

Status: LG24: G-LG23-4 partial (a call of a generic user function checks, domain first, the effective invariant of each instantiated parameter type on the argument, payload positions included, and assumes it for the instantiated result type when every type parameter of the callee sits in a walked parameter position, both verifiers; other callees keep the uninstantiated result, G-LG24-2)
Status: LG24: G-LG23-3 closed (the Err payload of `Result<T, E>` under `!is_ok` with `err_val`, and the variant fields of generic enum instances with type arguments substituted, are walked in both verifiers)
Status: LG24: G-LG23-2 open (array/`Vec` element invariants not done: a quantified element clause would have to survive loops that change the array, which needs a new loop frame analysis, G-LG24-1)

## What landed

- Generic call sites (G-LG23-4). The call-site rules of LG16/LG22/LG23 are applied to the instantiated signature of
  a generic user function. Each argument whose instantiated parameter type has an effective invariant is checked, the
  partial operations of the clause first (`ignore::<R>(r)`: "invariant of R (line L) for parameter x of ignore";
  `ignore::<Option<R>>(Some::<R>(r))`: "... for parameter x.some of ignore"). The domain proof is added to every
  struct-invariant argument check, generic or not, as the return check already had it. A parameter named `result` adds
  no argument clause at an instantiated signature (both verifiers; the non-generic declaration error is unchanged).
  The caller assumes the invariant for a result whose instantiated type has one (`id::<R>(r)`) only when the callee is
  parametric-safe: each type parameter occurs in the declared parameter types only directly, under `Option`, or under
  a two-argument `Result<T, E>` (E not `i64`); no such parameter is named `result`; and every type parameter of the
  result type occurs in a parameter. Otherwise the result keeps the uninstantiated assumption (G-LG24-2). Python
  computes the instantiated (requires, ensures) clauses in the checker next to the call's instantiation and the
  verifier uses them at the call; Rust substitutes the call's type arguments into the parameter and result types
  before building the clauses. The generic body is unchanged: it sees an abstract `T` and assumes nothing.
- Err payloads and generic enum variants (G-LG23-3). The invariant walk has two more steps: the Err payload of a
  two-argument `Result<T, E>` (guard `!is_ok`, value `err_val`, label `r.err`; `Result<T, i64>` is still the legacy
  `Result<T>` and is not walked) and the fields of each variant of a generic enum instance, with the type arguments
  substituted into the field types (guard `is_variant`, value `variant_field`, label `w.V.f`). The cycle guard keys on
  the full instance type. Every LG16/LG22/LG23 use of the effective set sees the new clauses.
- Array and `Vec` elements (G-LG23-2): not implemented (see the rule decision and G-LG24-1).
- SPEC.md section 6a, the struct invariant paragraph.

## Rule decisions

- Generic call sites: the argument checks are what a non-generic function with the instantiated signature would get,
  so they are always made. The result assumption rests on parametricity: the body can only return a `T` it received.
  That holds only when every received `T` was checked, so a callee with a `T` in a position the walk does not check
  (array, `Vec`, legacy `Result<T>`, generic user types; the review's `unwrap_or<T>(r: Result<T>, fallback: T)`)
  gets no instantiated result assumption. A body that needs a property of `T` has no way to state it (no trait
  bounds), so nothing is assumed inside the body.
- Err payload and generic enums: these are the same guarded clauses as LG23's Ok payload and non-generic enum
  variants, with the opposite guard and with substitution. Clauses with no guard are unchanged, so programs without
  these positions produce the same output (checked below).
- Array and `Vec` elements: the encoding would be one clause `forall i in 0..len(a): (!g || C[a[i]])` per element
  step, with guards before the element step outside the quantifier. Entry assumption, call argument and result use it
  directly, but an inout or local array that a loop writes loses the clause at the loop head unless a user loop
  invariant restates it. Programs that are accepted today and update such an array in a loop would then fail, unless
  the verifier carries the element invariant through the loop itself. That is a new loop frame analysis, so per the
  brief the step stops here (G-LG24-1) without a timing test of the encoding.

## Gaps

| Id | Gap |
|---|---|
| G-LG24-1 | Invariants of structs that are array or `Vec` elements are still not assumed or checked (was G-LG23-2). The clause would be `forall i in 0..len(a): (!g || C[a[i]])`, but an array written in a loop loses it at the loop head unless a user loop invariant restates it, so turning it on would reject programs accepted today. It needs the verifier to carry the element invariant through loops (a loop frame for the quantified clause) before it can be enabled. |
| G-LG24-2 | The instantiated result invariant of a generic call is assumed only when every type parameter of the callee sits in a walked parameter position (direct, `Option`, two-argument `Result`). A callee with a `T` inside an array, `Vec`, legacy `Result<T>`/`Result<T, i64>`, `Box` or a generic user type keeps the uninstantiated result; walking those positions (G-LG24-1 for elements) would let it be assumed. |
