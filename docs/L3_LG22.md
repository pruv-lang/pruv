# L3 LG22: struct field store destinations, `old` of inout struct parameters, nested struct invariants

Scope: G-DB31-1, G-DB31-2 and G-DB31-3 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is
changed. G-LG20-2/4/5, G-LG18-2/3, G-LG15-1, G-LG16-1 and G-LG21-x are out of scope and unchanged.

Status: LG22: G-DB31-1 closed (`store_le(inout s.f, ..)` / `store_be(inout s.f, ..)` on an array field of a local or inout struct, both compilers; only that field changes, an overlapping path in another argument is type/inout_alias)
Status: LG22: G-DB31-2 closed (`old(p)` and `old(p.f..)` of an inout non-generic struct parameter in ensures, both compilers; `old` of a non-inout parameter stays type/old_argument)
Status: LG22: G-DB31-3 closed (a struct's effective invariant includes the invariants of its plain struct-typed fields through the field path, assumed and checked wherever LG16 invariants are, both verifiers; step-3 program 0.03 s rs / 0.10-0.11 s py with no restated contract, vs 0.03-0.13 s / 0.10-0.13 s for the old compilers on the workaround)

## What landed

- Field place as store destination (G-DB31-1). The first argument of `store_le` / `store_be` may be `inout x.f` (a
  field chain ending in a `[u8]` field) of a local `let mut` or inout struct `x`, as the `copy_range` destination
  rules already allow. The verifier writes the new array into that field and rebuilds the struct value along the
  path, so the other fields keep their values. Aliasing: the offset or value argument may not mention a path of the
  same root that overlaps the destination path (a prefix of it, or extended by it); `x.g` for another field is
  allowed. The invariant is not checked at the store: LG16 invariants are handoff-only (assumed at entry, checked at
  return, calls and the struct literal), and a store inside a function body is no handoff; the next handoff checks it.
- `old` of an inout struct parameter (G-DB31-2). `old(x)` for an inout non-generic struct parameter is its entry
  value. `old(x.f.g)` is lowered by the checker into `old(x).f.g`, so the verifier only ever snapshots whole
  parameters; the struct inout parameters are snapshotted next to the array ones. A generic struct parameter, a
  non-inout parameter and any other operand stay type/old_argument.
- Effective invariants (G-DB31-3). The invariant set of a struct is its own clauses followed, in field order, by the
  effective invariants of each field whose type is a plain (non-generic) struct, rewritten through the field path;
  a struct already on the path is skipped (cycle guard). Each clause keeps its owner's struct name and invariant line;
  its label is the dotted path (`c.log`, `result.log`). Everything that used LG16 invariants (entry assumption of a
  parameter, exit check of an inout parameter and `result`, call-site check and assumption, the struct literal) uses
  the effective set. Array elements, `Option` payloads and fields of generic structs are not part of it (G-LG22-1).
- SPEC.md: the `store_le`/`store_be` paragraph, the struct invariant paragraph, the `old` bullet, R-6g-2 and the
  section 6 `old` line.

## Gaps

| Id | Gap |
|---|---|
| G-LG22-1 | Invariants of structs in other nested positions are not assumed: array elements, `Option` / enum payloads and fields of generic structs (a generic struct's invariant would need the instantiation in the effective set). Each needs its own encoding (quantified over elements, or under the payload's tag). |
| G-LG22-2 | `old` is still limited to whole inout array parameters and inout non-generic struct parameters with field chains; `old(a[i])`, `old(len(a))` style operands and `old` of a generic struct parameter stay type/old_argument. |
| G-LG22-3 | The effective invariant set has one clause per field path, so a struct that reaches the same invariant struct through many paths (for example `D1 { a: D0, b: D0 }` stacked n deep) gets 2^n clauses when it is used as a parameter or result. The value itself already has 2^n leaves, and the decision whether a struct has an invariant at all is linear (memoized reachability), but the clauses are not shared per field type. |
