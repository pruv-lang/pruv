# L3 LG25: borrowed `str` views of `str` and valid UTF-8 `[u8]` spans

Scope: G-DB32-1 and G-LG24-1 in both compilers (Python `pruvc/`, Rust `pruvc-rs/`). No `bench/` file is changed.
G-LG24-2, G-LG22-3, G-LG23-1, G-LG20-2/4/5, G-LG18-3, G-LG15-1, G-LG16-1 and G-LG21-x are out of scope and unchanged.

Status: LG25: G-DB32-1 partial (a `subview(x, lo, hi)` argument of a `str` parameter passes a borrowed `str` with no run-time UTF-8 or boundary check when the verifier proves the span valid UTF-8: from a `str` at char boundaries, or from a `[u8]` that is valid UTF-8 and cut at char boundaries or whose span is valid UTF-8, both compilers; a `[u8]` buffer assembled by copying several strings has no proven `utf8_valid` fact, so bench/l3/codex `span_ok` keeps its check, G-LG25-1)
Status: LG25: G-LG24-1 open (array/`Vec` element invariants not done: a loop that writes the array drops the quantified element clause at its head, so enabling it rejects accepted programs; carrying it needs a loop frame analysis, G-LG25-2)

## What landed

- String views (G-DB32-1), SPEC.md R-6g-10. `subview(x, lo, hi)` may be the direct argument of a non-`inout` `str`
  parameter. With a `str` source the verifier proves the range (`string_slice_range`) and both char boundaries
  (`utf8_boundary`), the same obligations as `substr`. With a `[u8]` source it proves the range (`index_oob`) and
  `utf8_valid(span) || (utf8_valid(x) && cb(x, lo) && cb(x, hi))` (`utf8_invalid`). The callee's parameter is the
  span (`len(t) == hi - lo`, `t[k] == x[lo + k]`). Verified Rust passes `x.get_unchecked(lo..hi)` (str source) or
  `str::from_utf8_unchecked(x.get_unchecked(lo..hi))` ([u8] source); LLVM passes the advanced pointer and the length.
  Safe mode (`--no-verify`) checks the range, then the boundaries or the bytes, and panics with the `substr` or
  `invalid UTF-8` message. A `str` source for an array parameter stays `type/type_mismatch`.
- Array and `Vec` element invariants (G-LG24-1): not implemented (see the rule decision and G-LG25-2).

## Rule decisions

- A view, not a ghost fact. The gap offered two fixes: a ghost "valid UTF-8" fact carried by `[u8]` values, or a
  borrowed `str` view of a byte range. The view reuses the LG6 view rules (R-6g-5..9: direct argument, non-`inout`,
  place source, no nesting) and the existing `utf8_valid` and `is_char_boundary` model, so no new type state is
  needed and the proof obligation sits at the one place the bytes become a `str`.
- The `[u8]` obligation is a disjunction. `utf8_valid(span)` covers spans whose own bytes are known (ASCII or
  proven valid); `utf8_valid(x)` with boundary cuts covers spans of a valid buffer. Cutting valid UTF-8 where no
  continuation byte starts leaves complete sequences on both sides, so each piece is valid.
- Codes: a `str` source reports what `substr` reports, a `[u8]` source reports what an array view (`index_oob`) and
  `str_from_utf8` (`utf8_invalid`) report, so no new error code.
- Element invariants: the encoding would be `forall i in 0..len(a): (!g || C[a[i]])`. Loops havoc every array they
  assign and keep only user or inferred invariants, so an accepted program that writes such an array in a loop and
  then passes or returns it would fail its invariant check. The `--infer` candidate mechanism could propose the
  clause as a loop invariant, but dropping a failing candidate still loses the fact downstream, so the flip remains.
  Carrying the clause through loops is a new analysis; per the brief the step stops here (G-LG25-2) without a timing
  test of the encoding.

## Gaps

| Id | Gap |
|---|---|
| G-LG25-1 | A `[u8]` buffer filled by copying the bytes of several `str` values (bench/l3/codex `hb` arena) has no proven `utf8_valid` fact: the copy loops keep only stated invariants, and "concatenation of valid UTF-8 is valid" is not in the model, so `span_ok` cannot be replaced by a view there. It needs a loop invariant form for "the prefix `0..k` is valid UTF-8 and ends at a boundary" (or a ghost UTF-8 fact on `[u8]`) before the bench check can go. |
| G-LG25-2 | Invariants of structs that are array or `Vec` elements are still not assumed or checked (was G-LG24-1). The clause would be `forall i in 0..len(a): (!g || C[a[i]])`, but an array written in a loop loses it at the loop head unless a user loop invariant restates it, so turning it on would reject programs accepted today. It needs the verifier to carry the element invariant through loops (a loop frame for the quantified clause) before it can be enabled. |
