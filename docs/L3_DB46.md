# L3 DB46: codex M RSS regression and per-read scratch (G-DB44-1, G-DB44-2, G-DB44-3)

Brief: find and fix the M RSS rise from DB44 (G-DB44-1) by measurement, find which buffer makes one empty read cost
0.57-0.66 MB over runtime (G-DB44-2), and re-check the old baseline L of DB44 (11.2 MB against DB40's 8.6 MB). Base:
main e755df93. The rs compiler was built once from this base; no other compiler build. G-DB40-1 and compiler changes
are out of scope.

## What landed

- `bench/l3/codex/root.pruv`: the held turns start at offset 0 again (`hs[1] = 36864` removed). `hb` is still
  `byte_buffer(65536)`.
- `bench/l3/codex/read.pruv`: `replay` takes `used` (the bytes `absorb` wrote, `hs[1]`). Once per read, if the newest
  held turn starts before `front = 8*(20 + 10*count + 2*items) + base` (the header + base when every held turn is
  kept, which is at or after the real wire start `at`), it grows `hb` to `used + front` with `resize` (prefix kept) and
  moves the used bytes right by `front` with `copy_within` (overlap safe). Every `ht` offset it reads gets `+ sh`;
  the `-1` stamp sentinels stay. Spans must end at or before `used + sh`, not only `len(hb)`, and `used` outside
  `0..len(hb)` sets `bad` for every `count` (both from the audit). `finish_inplace` and the rest of the in-place path
  are unchanged.

## G-DB44-1 cause

DB44 reserved the first 36,864 bytes of `hb` so that the held turns always start at or after the wire start. At M the
held text is 229,882 bytes, so `hb` needed about 266,746 bytes, just over 262,144: `grow_bytes` doubled once more to
524,288 bytes, and that doubling copies old + new. That is the +0.5-0.67 MB on every M cell. At L the text needs
about 1 MB either way, so the reserve did not cross a doubling and L kept its gain. Checked by measurement before the
fix was written: a scratch rs/rust build with the shift instead of the reserve (no verify, same host) gave M1 RSS
3,473,408 vs 3,964,928 (DB44 code) and M 4,816,896 vs 5,701,632, hand 2,605,056 / 2,981,888, time unchanged
(M 85.68 vs 84.99 ms, L 219.12 vs 218.09 ms), 9 alternating rounds at load 6-7. The fix costs one memmove of the used
bytes per read, and a `resize` only when `used + front` is past `len(hb)` (once, after the per-page growth chain,
not inside it). At M, `hb` is 262,144 bytes after the chain and `used + front` fits, so no resize happens.

## G-DB44-2 attribution (E1 - E0, one process per sample)

`/usr/bin/time -l` gives both the max RSS and the "peak memory footprint"; the footprint leaves out clean pages
(code and read-only data mapped from the binary).

| side | E1 - E0 RSS | E1 - E0 footprint |
|---|---|---|
| hand | +147 KB | +16 KB |
| Pruv rs/rust (DB44 code) | +623 KB | +295 KB |

So about 0.31 MB of the excess is clean code pages that the first real read touches (the Pruv runner text is
0.17-0.33 MB larger than hand: compiler output and runtime, outside this lane), and about 0.28 MB is dirty data.
Scratch variants of the dirty part (rs/rust, no verify):

- `hb` 64 KiB -> 4 KiB: about -16 KB.
- runtime event reader buffers 64 KiB -> 4 KiB: no change.
- three extra unused zeroed buffers (32 + 64 + 18 KiB): +65-82 KB, so about 70% of a zeroed buffer ends up dirty.

The lane buffers left are `chunk` (64 KiB, `rpc::open` requires `len(chunk) == 65536`, in `bench/l3/lib/`), `pb`
(18,024 bytes) and `fb` (32,768 bytes), both required by `absorb`'s contract. Making `pb` / `fb` lazy would save at
most tens of KB, so it was not done. The rest of the dirty data is runtime (event writer / reader / timer threads and
their stacks) and the JSON documents, outside this lane (G-DB46-1, G-DB46-2).

## Old baseline L (DB44 11.2 MB vs DB40 8.6 MB)

The sources did not change between DB40's merge (e8fbe198) and DB44's base (f3919ed2): `git diff` is empty for
`bench/l3/codex/`, `bench/l3/pkgs/`, `bench/l3/lib/` and both compilers. Rebuilding f3919ed2 rs/rust here gives L
median 8.65 MB (7.77-9.44 MB over 15 samples), the DB40 value, so 11.2 MB does not come from the f3919ed2 code. The
DB32-era runners measured 10.4-10.5 MB at L, so the most likely cause is that DB44's `/tmp/db44_base` runners were
stale (built from an older tree, not from f3919ed2); that directory is gone, so this cannot be confirmed. DB44's new
numbers also ran high: its tree measures L 5.5-6.8 MB here (verified rs/rust median 5.64 MB) against 7.78 MB in the
DB44 table, so the run state of that measurement (load, other work) is the other part of the gap. Old/new in this
doc are both built from known commits in the same run.

## Audit (Codex gpt-6.2-astra ultra, once)

It found the shift consistent on the real `root -> absorb -> finish` path: `front >= at` (`front - at = 80 x
(count - kept)`), `resize` keeps the prefix and `copy_within` is overlap safe, every `ht` offset gets `sh` once, the
`-1` stamps are kept, and the only new cost is one move of `used` bytes per read outside the per-turn loop. Two
must-fix, both reachable only by calling `replay` with inputs `absorb` does not produce: a span past `used` (but
inside `len(hb)`) was accepted, and `used` out of range with `count == 0` was not flagged. Both fixed (spans are
checked against `used + sh`; the `used` check no longer depends on `count`), then re-verified on all four pairs by
the test run below. No recheck (the fix only adds rejections; the test run is the check).
